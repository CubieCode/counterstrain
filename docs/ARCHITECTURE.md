## Repository and products

```text
                 ┌───────────────────────────────┐
                 │ Counterstrain (pack/)         │
                 │ KubeJS · FTB Quests · datapack│
                 │ story, recipes, balance       │
                 └──────────────┬────────────────┘
          data/scripts only     │  (tags, per-mob JSON, recipes, triggers,
          never Java imports    │   stats, commands, API events via KubeJS)
                 ┌──────────────▼────────────────┐
                 │ Remission (mod/)              │
                 │ generic defaults, no pack deps│
                 └──────────────┬────────────────┘
                                │ optional, guarded integrations
              Mekanism · AE2 · Create · Ars Nouveau · EMI/JEI · JourneyMap
              and the phase 10 mod-side tie-ins (DESIGN: Pack integrations)
```

- Remission requires only NeoForge. Integrations with other mods are optional (`compileOnly` against the mod, declared `type="optional"` in `neoforge.mods.toml`, runtime checks via `ModList`) and live in `integration/<modid>/`; Mekanism (P7.1) is the first. Remission never hard-depends on an integrated mod.
- Integrations and addons build on the public API (`com.cubiecode.remission.api`, below). Pack-side integration (KubeJS, datapacks) is preferred; mod-side code is used only where the other mod's content can be registered or hooked only from Java (DESIGN, Pack integrations).
- The pack talks to the mod only through data and script surfaces (below). If the pack needs something the mod cannot express, extend the surface generically rather than special-casing the pack.

## Naming in code

Internal Java system names and public API types may keep the generic word "corruption" (`CorruptionState`, the `corruption` attachment, `remission:is_corrupted`); content IDs, lang keys, triggers, stats and commands use the Strain glossary in [DESIGN](DESIGN.md#glossary). ## Planned systems and data flow

### Corruption state (phase 2, built in P2.1)

- `CorruptionState(level, stage)` in `corruption/`: `level` 0–100 (`MAX_LEVEL`), `stage` the number of `hosts.stageThresholds` entries the level met when it was set (default `[1, 34, 67]`, so stages 1–3; 0 means not a host). `variant` (the resistant mutation a host carries) is reserved for P7.5 and not stored yet. Field-level contract: remission-data-formats.
- Attachment `remission:corruption` (`RemissionAttachments.CORRUPTION`) on any entity; the API takes `LivingEntity`. Codec-serialized with the entity (`neoforge:attachments`), skipped at level 0, so it survives save/reload and dimension change (non-player entities are recreated with `restoreFrom`, which copies saved data; players keep their entity). Not copied on death or by vanilla living conversions; infection's own `convert_to` sets it on the replacement (below).
- Server API `Corruption.get(entity)` (never creates the attachment), `Corruption.set(entity, level)` (clamps, restages from config, removes the attachment at 0, no-op if unchanged, throws on the client), `Corruption.isHost(entity)`, `Corruption.isImmune(entity)` (`#remission:immune`; `set` ignores levels above 0 for immune entities). `set` applies or removes mob profile attribute modifiers when host status changes, then posts the API's `HostCorruptedEvent` or `HostCleansedEvent` when the state changed; `set(entity, level, cause)` names the `CorruptionCause` (infection on kill passes `INFECTION`, festering land infection `FESTERING_LAND`, the debug commands `COMMAND`, the two-argument form `OTHER`).
- Stages are computed when a level is set, never on load or on the client, because common config is not synced and may differ per side. Changing the thresholds restages a host only when its level next changes.
- **Sync decision: NeoForge attachment sync** (`AttachmentType.Builder#sync(StreamCodec)`, present in 21.1.259), not a custom payload. NeoForge's `AttachmentSync` sends `setData`/`removeData` changes to `chunkMap.getPlayersWatching(entity)` plus the entity itself when it is a player, sends the full state in the start-tracking pairing data (`ServerEntity.sendPairingData`), and resends a player's own attachments on login, respawn and dimension change. That covers every case P2.1 requires with no Remission code, removal included. Synced attachment types are a synced registry, so client and server must both have Remission (already required: `side="BOTH"`). `RemissionNetwork.PROTOCOL_VERSION` is unchanged; the wire format is `CorruptionState.STREAM_CODEC` (two var-ints), so changing it is a protocol change for the synced registry. A custom payload would only be worth it for batching or per-player filtering beyond tracking, which nothing needs yet.
- Client: `HostOverlayLayer` draws hosts from the synced state (host rendering, below).

### Host rendering (phase 2, built in P2.2, layers in P2.4)

- `HostOverlayLayer` is added in `EntityRenderersEvent.AddLayers` to every renderer that is a `LivingEntityRenderer`: each `getEntityTypes()` renderer plus every player skin renderer. No per-entity-type code, so modded mobs get it too. Renderers that are not living-entity renderers (the ender dragon's, GeckoLib-style renderers) cannot take layers and are skipped; the count is logged at startup. At render time the layer also skips a null model or texture, invisible entities and non-hosts.
- The layer re-renders the parent model after the mob's own pass, so it inherits that frame's pose, baby scaling and model-part visibility. It calls `setupAnim` again with the frame's arguments before each pass, because some models keep per-draw state and clear it after drawing (Mekanism's robit model drops its entity and would draw nothing); vanilla `setupAnim` is idempotent. Armour, wool and other own-model layers get their own companion (below); held items are not overlaid.
- Render type `remission_host_overlay` (`HostRenderTypes`, memoised per mob texture, pattern and layering state): shader `remission:host_overlay` (vanilla `rendertype_entity_translucent` vertex stage, own fragment stage), translucent blending, no culling, lightmap and hurt overlay, colour writes only. It binds the mob's texture to sampler 0 and the Strain pattern to sampler 3, and discards fragments where the mob texture is transparent, so empty outer-layer boxes (hats, jackets, the drowned's outer layer) stay invisible. The pattern repeats at one pattern texel per mob texel whatever the mob texture's size.
- Stage drives the look: `textures/entity/host/stage_1..3.png` (stages above 3, from extra thresholds, use stage 3), plus a full-bright `veins_glow.png` pass from stage 3. The client reads only the synced `stage`; it never restages. All four textures are placeholders (CONTENT-PROVENANCE).
- Client config `hosts.overlayIntensity` (0–1, default 1) is the overlay's vertex alpha; 0 turns it off. Presentation only.
- Layers with their own model or texture (P2.4): `HostLayerOverlay` adds, in `AddLayers` at `EventPriority.LOWEST` (so layers other mods add in the event are seen), one companion per `HumanoidArmorLayer`, `SheepFurLayer`, `SlimeOuterLayer`, `DrownedOuterLayer`, `HorseArmorLayer` and `WolfArmorLayer` (or subclass) in every living-entity and player skin renderer, vanilla or modded, appended with `addLayer` to the end of that renderer's layer list (after eyes, held items and the other layers), not next to the layer it wraps. For a host it runs the wrapped layer again (once per pattern, plus the glow pass from stage 3) with a buffer source that sends each `NEW_ENTITY`-format draw into `remission_host_overlay` for that draw's own texture and layering state (armour is drawn with `VIEW_OFFSET_Z_LAYERING`, nudged towards the camera, and an un-offset overlay would lose the depth test), with the overlay colour instead of the layer's dye; glint (other vertex format), the armour-trim atlas and outlines are dropped. The layer's own logic therefore picks the pieces, models and textures (NeoForge custom armour models and textures included), and the overlay follows each layer texture's cutout. Eye and emissive layers (`EyesLayer`, energy swirls) are never wrapped. Reading the renderer's `layers` list and a render type's texture uses reflection (`ObfuscationReflectionHelper`, Mojang names at runtime) rather than a mixin or access transformer. Failures degrade without crashing: if the reflective handles cannot be resolved, one error is logged and no companions are added; if a renderer's `layers` list cannot be read, one warning per such renderer and it gets none; if a render type's texture cannot be read, one warning per failing render type (the empty result is cached) and draws of that type get no overlay. Nothing else changes. Where two draws of one layer cover the same texels (leather's undyed overlay, dyed or cracked wolf armour) the pattern is applied twice there and looks slightly stronger. A wrapped layer must not hold two entity-format buffers open at once (vanilla's do not); the overlay buffers would end each other's batch.
- Limits: other layers (saddles on pigs and striders, llama decor, villager and horse markings, held items, heads, elytra, capes) are not overlaid; renderers that are not `LivingEntityRenderer`s (GeckoLib-style) get nothing. Stage particles (DESIGN) are not built yet.
- Harness scene `corruption/stages_layers` (P2.4) shows stages 0–3 on armoured zombies (iron, dyed leather), a skeleton, a fully armoured armour stand, a drowned, white and red sheep, a slime, a wolf in wolf armour and a horse in iron horse armour, plus the armoured player at stage 3 in third person.
- Harness scenes `corruption/stages_vanilla` and `corruption/stages_modded` (visual-checks) show stages 0–3 on a vanilla lineup (baby, armoured, player in third person) and on the Mekanism robit with non-standard vanilla renderers (armour stand, slimes, guardian). The wither and the ender dragon are immune bosses (`#c:bosses` in `#remission:immune`, P3.3): the scene still corrupts them, but they stay clean beside the hosts, so the `ender_dragon` shot (a renderer without the layer) and the wither now show an immune boss rendering normally.

### Research (phase 6, built in P6.1)

- `remission:scanner` makes data items: a host gives `remission:host_scan`, a block gives `remission:block_scan`, a living non-host gives nothing. The data item carries the `remission:scan_data` component (`ScanData`: host entity type id and stored host stage, or block id), registered in `RemissionDataComponents` as persistent and network-synchronized. Field contract: remission-data-formats ("Scanner and data items").
- The server decides and writes; the client only claims the interaction (arm swing). Entity scans run from `PlayerInteractEvent.EntityInteract` / `EntityInteractSpecific` so they come before the target's own interaction (villager trading, mounting); block scans run from `onItemUseFirst`, before the block's use. A 20-tick item cooldown follows every attempt and also stops a double scan when both entity events fire.
- Feedback is a vanilla action-bar message; no payloads. The scan reads host state through `Corruption.get` and never changes it.
- No timestamp or player is stored, so identical scans stack and recipe ingredients can match the full component value (NeoForge components ingredient).
- Each host scan fires `remission:host_scanned` and counts `remission:hosts_scanned`; each block scan fires `remission:block_scanned` and counts `remission:blocks_scanned` (P8.1). The sequencer consumes scans (`#remission:scans`, P7.2). The scanner sits in the vanilla Tools and Utilities tab until Remission has its own creative tab.
- Harness scene `research/scanner` (visual-checks): the three items in item frames, and an armour stand pointing the scanner at a stage 2 host cow.

### Research: bestiary (built in P6.2)

- Host types are not a list: `Bestiary.isHostType` takes every registered entity type that has default attributes (every living type must register them, so this needs no entity instance), is not `minecraft:player`, and is in neither `#remission:immune` nor `#remission:bestiary_hidden` (P6.3). Installed mods widen it at once (79 types in dev runs with Mekanism: vanilla plus the robit). Players can still carry the Strain and be scanned as hosts; they are just not a bestiary entry. `#remission:bestiary_hidden` keeps infectable types that survival players cannot normally meet as hosts out of the list and total: Remission ships giant, illusioner and armour stand, and packs extend or replace it. It is a tag rather than a heuristic such as "has a spawn egg", which would drop modded mobs like the robit.
- Progress is the player attachment `remission:bestiary` (`BestiaryProgress`: entity type id → highest host stage scanned). `Scanning.scanEntity` calls `Bestiary.recordScan` on the server whenever it gives a host scan; only bestiary host types are recorded (a scanned host player, for one, is not), and a lower stage never lowers the record. Saved with the player (only when non-empty) and copied on death. Synced through NeoForge attachment sync, so no custom payload and no `PROTOCOL_VERSION` change: updates go to the owning player only (`Bestiary.syncsTo`), but NeoForge's initial sync when a client starts tracking an entity ignores that predicate, so clients tracking the player also receive the current map. That is harmless: the screen reads only the local player's progress. Field contract: remission-data-formats ("Bestiary").
- Client: `client/research/BestiaryKeys` (a `Dist.CLIENT` subscriber, not `RemissionClient`) registers the key mapping `key.remission.bestiary` (category `key.categories.remission`, default M, in game only) and opens `BestiaryScreen`, a read-only vanilla list: header "X of N host types scanned" (lang `gui.remission.bestiary.progress`), one row per host type (spawn egg icon if the type has one, name, mod name, highest stage scanned or "Not scanned"), scanned types first, then by mod (vanilla first) and name. The client computes the host types itself from its registry and the synced entity type tags. No custom GUI art.
- Harness scene `research/bestiary` (visual-checks): shot `hosts` shows the scanned hosts in the world, shot `list` opens the bestiary through the key mapping.

### Behaviour (phase 3, goals and attributes built in P3.1, fallbacks in P3.2)

- **When:** `HostBehaviours.update(mob)` brings a `Mob`'s goals in line with its host state. It runs on `EntityJoinLevelEvent` (server, low priority so other mods' goals are in first) and from `Corruption.set`, so `/remission infect`, `cleanse` and any later infection source act on loaded mobs at once. Nothing runs per tick. It is idempotent: a host that already has host goals, or a non-host without them, is left alone. `Corruption.set` calls it directly, before posting the host corrupted / cleansed events (P4.4), so listeners see a host with its goals in place.
- **State:** what was removed and added (goal, priority) lives in the transient attachment `remission:host_goals` (`AppliedHostGoals`): never saved, synced or copied. Goals are not saved either, so a mob loaded from disk rebuilds its own goals and gets host goals again on join if it is still a host; a mob cleansed before saving loads as a normal mob. Cleansing a loaded mob restores its stripped goals at their old priorities and removes the added ones in-session, and clears its target.
- **Behaviour seam:** `HostBehaviours.behaviourFor(mob)` returns the mob's `MobBehaviour` and is the only place goal application asks. Profile first: the `behaviour` of the mob's `remission:mob_profile` (`MobProfiles.find`) when it sets one, else `HostBehaviours.categoryDefault(mob)`. Overloads `behaviourFor(mob, profile)` and `update(mob, profile)` take an explicit profile (tests). Because goals are applied once per host transition and on join, a changed profile reaches loaded hosts on the world reload that loads it. Category defaults, first match wins: for brain-based mobs (any registered memory, `HostBehaviours.isBrainBased`), `melee` when the brain registers `attack_target`, the memory its fight activity acts on (piglins, piglin brutes, hoglins, zoglins, axolotls, breezes, wardens, frogs), else `none` (villagers, allays, goats, camels, sniffers...); `flying` for `FlyingMob`, `FlyingAnimal`, `AmbientCreature`, category `ambient` or flying navigation (bats, parrots, bees, ghasts, phantoms); `swimming` for `WaterAnimal`, the water categories or water-bound navigation (fish, squid, dolphins, guardians); `ranged` for `RangedAttackMob` (skeletons, snow golems, llamas, witches); `melee` for everything else (cows, sheep, pigs, zombies, spiders, slimes, modded goal-based mobs).
- **Default profile:** `remission:unsupported` (priority -1000) marks villagers, allays and frogs `none`: their brains cannot fight a chosen target (no fight activity; a frog's tongue only takes frog food). They still become hosts and render as hosts; they just keep their own AI. Contract: remission-data-formats, Mob profile.
- **What each value does** to a goal-based host:
  - `melee`: strips passive goals (breed, tempt, avoid/flee, panic, follow parent/owner/mob/boat/caravan, sit, beg, shoulder, run around, trading) and the whole target selector, then adds `HurtByTargetGoal` (priority 1, pathfinders only, no alerting), `NearestAttackableTargetGoal<Player>` (2) and `NearestAttackableTargetGoal<LivingEntity>` (3), both line-of-sight and limited to attackable non-hosts. If the mob has no attack goal (`MeleeAttackGoal`, `RangedAttackGoal`, bow or crossbow goal) it gets `MeleeAttackGoal` (priority 1, speed 1.2) when it is a `PathfinderMob`; other mobs (slimes) keep attacking through their own goals.
  - `ranged`: as `melee`, but a mob without an attack goal gets `RangedAttackGoal` (speed 1.0, 40 ticks, radius 12) when it is a `RangedAttackMob`.
  - `passive_hostile`: strips the same goals, adds only `HurtByTargetGoal` and an attack goal: it never picks fights but fights back against anything except hosts.
  - `flying`, `swimming`: strips and targets as `melee`, then adds `HostPursuitGoal` (priority 1, move and look) instead of a melee goal, whatever attack goals the mob has. It closes on the target and calls `doHurtTarget` in melee reach every 20 ticks, so damage is the `attack_damage` attribute (2 by default; profiles raise it). Movement: flying or water-bound navigation when the mob has it and a path exists (parrots, bees, fish, dolphins), else it steers the mob's velocity straight at the target at about 0.35 blocks per tick (bats, which steer themselves and have no flying navigation); vanilla squids move only along their movement vector, so a squid is steered through `Squid.setMovementVector`. A resting bat is woken whenever it settles mid-chase. A host bee stings on every hit (the pursuit goal ignores `hasStung`, so each hit poisons) and, as in vanilla, dies some time after its first sting. A `swimming` host pursues only while it and its target are both in water, so fish never beach themselves chasing land prey. Monsters (`Enemy`: ghasts, phantoms, guardians, modded flying monsters) get no pursuit goal: they fight whatever target Remission's target goals give them with their own goals (fireballs, swoops, lasers).
  - `none`: no goal changes (villagers, allays and other brain mobs that cannot fight, and an explicit opt-out for profiles).
- **Brain-based hosts** (no mixins): brain AI ignores goals, but `Mob.serverAiStep` still ticks the goal and target selectors of every mob. For a brain mob, every attacking behaviour (`melee`, `ranged`, `flying`, `swimming`) strips as above and adds `BrainHostTargetGoal` (target selector, priority 2, no flags) instead of target and attack goals. Every 10 ticks it keeps the brain's `attack_target` memory on the nearest visible prey within `follow_range` capped at 16 blocks, the range vanilla brain sensors and piglin and breeze target checks use (players first, then any attackable non-host). Fight activities drop targets their own checks reject, so on every pass, including while the current target stays valid, it also feeds what those checks read: `angry_at` for 600 ticks where the brain registers it (piglins and piglin brutes keep only a target they are angry at or chose), and for a warden, anger at the target up to `angry` plus a 1200-tick dig cooldown (a warden fights only while angry at its target, and one that did not emerge has no dig cooldown, so it would dig away instead). The brain's own fight activity then moves and attacks (piglin melee or crossbow, hoglin tusks, axolotl bites, warden roar, melee and sonic boom, breeze wind charges), so reach and damage are the mob's own. A breeze still attacks only players and iron golems (`Breeze.canAttackType`). A brain without `attack_target` keeps its own AI even if a profile asks for an attacking behaviour. `passive_hostile` changes nothing on a brain mob, which already retaliates through its brain. Cleansing removes the goal and erases `attack_target` and `angry_at`.
- **Hosts never target hosts:** a `LivingChangeTargetEvent` listener clears any target a host would set on another host, for every host whatever its behaviour (brain `StartAttacking` included). Target goals re-set their target each tick they continue, so a target that becomes a host mid-fight is dropped on the next tick.
- **Attributes:** `EntityAttributeModificationEvent` adds `attack_damage` (default 2) and `follow_range` (default 32) to every entity type with attributes that lacks them, so attack and target goals work on any mob. Profile attribute modifiers (`HostAttributes`, P3.3) are applied in `Corruption.set` before host goals.
- **Tests:** `HostFallbackTests` (own batch `host_fallbacks`, `remission:host_arena`, flooded for swimmers): host bat and parrot hurt a pig; ghasts and phantoms get target goals but no pursuit goal; host cod, squid and dolphin hurt a salmon in water; a host cod on land ignores an adjacent pig; host piglin, hoglin and warden hurt a pig, a host axolotl hurts a dolphin and a host breeze hurts an iron golem; villagers, allays and frogs resolve to the default profile's `none` and get no host goals; a pack's priority 0 frog profile without `behaviour` replaces the default and the frog falls back to `melee`; cleansing a piglin removes its brain goal and attack target. `HostBehaviourTests` (own batch, `remission:host_arena`): host cow, zombie and Mekanism robit (dev runtime only; skipped without Mekanism) hurt an uninfected pig; a host sheep hurts a survival player; hosts ignore hosts (including retaliation and a forced `setTarget`); a target that becomes a host is dropped; cleanse restores goals in-session; reload re-applies host goals on join and a cleansed save loads normal; category defaults; every living type has the attributes.
- **Harness scene** `behaviour/fallbacks` (shots `brain`, `flying`, `swimming`): stage 2 hosts of each category (brain mobs on a floor and flyers, a ghast standing in for flying monsters, in the air, each beside an uninfected pig; swimmers on a dry floor, because animated water textures and the phantom's id-offset wing flap are not pinned by the frozen tick and made shots differ between runs), so the overlay is checked on every fallback category. Ticks are frozen in harness scenes, so pursuit itself is covered by the gametests. Infection: below (P3.3).

### Infection, mob profiles and host loot (phase 3, built in P3.3)

- `Infection` listens to `LivingDeathEvent` at `LOW` priority. A dying `Mob` whose damage source's responsible entity is a host is not killed: the event is cancelled and it becomes a host at the lowest stage threshold, in place (healed, same entity, no death loot) or, with a profile `convert_to`, replaced through `Mob.convertTo` with NeoForge's `LivingConversionEvent` pre/post. In-place keeps the entity's data (trades, owner, inventory); the replacement joins the level before it is infected, and `Corruption.set` then applies its attributes and host goals.
- `#remission:immune` (default `#c:bosses` only; players stay infectable for the overlay, scanning and commands, and infection on kill never takes them because it only converts `Mob`s) is enforced in `Corruption.set`, so every route (infection, conversion, commands, future sources) respects it.
- Festering land infection (P4.7, below) goes through the same conversion path with `CorruptionCause.FESTERING_LAND`; `Infection.canInfectFromFesteringLand(Mob)` checks its eligibility (immune, host, profile flag). Contact infection (P4.8, below) uses the same eligibility and path with `CorruptionCause.CONTACT`.
- `remission:mob_profile` is a server-only datapack registry (`DataPackRegistryEvent.NewRegistry`, no network codec). **Reload decision:** datapack registries are read when a world loads and are frozen afterwards, so profile changes need a world reload; `/reload` only rebinds the tags profiles name. Making profiles `/reload`-able would mean a `SimpleJsonResourceReloadListener` with its own tag resolution; the registry was kept because HolderSet entity matching, error reporting and KubeJS/datapack tooling come for free, and profiles are tuning data rather than something changed mid-session. `MobProfiles.find` sorts by id and picks the highest priority on every call (no cache; it runs on infection and host transitions, not per tick).
- `HostAttributes` applies a profile's `attributes` as permanent `add_value` modifiers (`remission:mob_profile`), so they save with the entity and a host's health above its base maximum survives reload; it removes them on cleanse and reconciles them when a host joins a level.
- Loot: `remission:is_corrupted` reads the stored stage of a loot context entity. The default global loot modifier `remission:host_samples` (codec `remission:add_item`) adds one `remission:host_tissue` to a host's death loot; `minecraft:damage_source_properties` with no predicate keeps it to death drops.
- Gametests: `InfectionTests`, `MobProfileTests` (including a profile `behaviour` overriding the category default in applied goals), `HostLootTests`. The phase exit scene `behaviour/conversion` was outside P3.3's assigned scope and is still open.

### Festering land (phase 4; levels, nidi and spread built in P4.1)

- Chunk attachment `remission:chunk_corruption` (`RemissionAttachments.CHUNK_CORRUPTION`): `ChunkCorruption(level, last_update_game_time)`, level 0–100, saved with the chunk (never at level 0), server only (no sync: clients see stages through the festering blocks and the flipped biome, P4.2, which reach them as ordinary block and biome updates). The spread engine only raises levels; purification (P5.2, below) lowers them. Field-level contract and config: remission-data-formats.
- Nidi: block `remission:nidus` (`NidusBlock`, block entity `NidusBlockEntity`, drops a nidus core since P7.1, pistons cannot move it). `NidusIndex` is a `SavedData` per level (`data/remission_nidi.dat` in the dimension folder) mapping each nidus position to the game time it was indexed. `onPlace` and the block entity's `onLoad` (covers nidi placed by worldgen or structures) add it; `onRemove` removes it, and a pass that finds a loaded index entry without its block drops it. Breaking a nidus stops its spread at once; its land keeps its level.
- Spread engine (`SpreadEngine`, one per server level, run from `LevelTickEvent.Post` by `FesteringLand`): a pass starts at each multiple of `spread.intervalTicks` of level game time and visits, nidus by nidus in index order, every chunk within the nidus's Manhattan radius, nearest first. The nidus chunk gains `nidusGrowth` per pass up to 100. Another loaded chunk at distance `d` gains `spreadStep` up to `100 - d * falloff` from its parent, the neighbour one step closer to the nidus along the larger offset axis, once the parent has reached `spreadThreshold` (an unloaded parent counts as at its own target). The radius follows from those numbers (7 chunks by default). A pass stops after `chunkBudget` chunk visits and resumes next tick. Nothing depends on iteration order of hash maps or on wall time, so the same state and the same ticks give the same levels (gametest `spreadIsDeterministic`). Overlapping nidi each add their step.
- Catch-up: `ChunkEvent.Load` only queues the chunk (the chunk is not yet in the level then); each tick up to `catchUpBudget` queued chunks are fast-forwarded in closed form: for each nidus in reach, the passes missed since `max(last_update_game_time, nidus indexed)` times the rate, capped at the target. Like a live pass, it holds a step whose parent is loaded and below `spreadThreshold` (an unloaded parent counts as at its target), so a firebreak holds after a reload while the firebreak chunk is loaded; a chunk whose loaded, below-threshold parent is itself still queued catches that parent up first (recursively, at most `radius` deep, stopping at cycles between nidi; the parent's own queue entry is then skipped), so a region that loads at once catches up from the nidus outward in any load order (gametests `catchUpRespectsFirebreak`, `catchUpOrderDoesNotMatter`). A live pass skips a chunk still queued for catch-up (P4.5), so a pass that comes due before a backlog drains cannot step it and move `last_update_game_time` to now; the catch-up then credits every pass it missed, the skipped one included (gametest `livePassWaitsForCatchUp`). That converges on the same targets as live spread, so land keeps festering while nobody is near, and a reload costs the same however long it was away. Unloaded chunks are never loaded by the engine.
- Hooks: `SpreadHooks` posts the public land events (P4.4): `spreadAttempt` posts `StrainSpreadAttemptEvent` before each chunk-to-chunk step, live and catch-up, and returns the amount scaled by its multiplier (fraction resolved by a hash of the step and game time, so spread stays deterministic), 0 if cancelled; `chunkLevelChanged` posts `ChunkStageChangedEvent` after a change that moves the chunk's festering stage (`[festering] stageThresholds`; one per chunk for a catch-up); `nidusDestroyed` posts `NidusDestroyedEvent` after removal from the index, with the destroying player and contributors when a player destroyed it (P4.10, below), otherwise none.
- Festering stage: a chunk's stage is the number of `festering.stageThresholds` (default `[1, 25, 50, 75]`) its level meets, computed on the server from the current config whenever it is needed, never stored. P4.2 applies it to the land (below).
- Measured cost (foundry, `SpreadBenchmark`, below): default config with 16 nidi over 1,024 loaded chunks adds 0.9 µs per tick on average and at most 0.13 ms in a tick (about 0.34 ms per 400-tick pass); a stress case of 64 nidi with a pass every second spends the full 256-visit budget every tick at 27 µs mean and 0.09 ms max. Catching up 1,024 chunks took 32 ticks at most 0.18 ms (16 nidi) or 0.29 ms (64 nidi) each in P4.1; with P4.4's parent-first rule it is still 32 ticks, at up to about 0.3 ms (16 nidi) or 0.9 ms (64 nidi) each (Public API, below).

### Festering stages and biome flip (phase 4, built in P4.2)

- `FesteringStages` turns a chunk's stage into land. A stage rise (`ChunkStageChangedEvent` from the spread engine, live or catch-up) or a chunk load queues the chunk per level; each `LevelTickEvent.Post` does up to `COLUMN_BUDGET` (64) units, one per column festered or queued chunk skipped, so a chunk takes 4 ticks, then queues it for the cave pass (P4.6, below). Work reads the chunk's stage when it starts. A chunk that leaves full status mid-way (or is queued while not at full status) is parked and queued again when it is back at full status or, if it unloads, by its load event.
- Per column, from the `WORLD_SURFACE` height down through trees, plants and water to `GROUND_DEPTH` (5) blocks into the ground (first block that blocks motion and is not a log or leaves), each block whose `remission:festers_into` data map entry has `stage` ≤ the chunk stage is replaced, keeping shared state properties, with flags `UPDATE_CLIENTS | UPDATE_KNOWN_SHAPE` (no neighbour updates, so no decay or drop cascades; light is updated by `setBlock` as usual). Block entities are skipped. `BlockFesteredEvent` is posted per replaced block.
- At the last stage (`CorruptionQueries.maxChunkStage()`), after the blocks, `flipBiomes` rewrites every biome cell of the chunk through `ChunkAccess.fillBiomesFromNoise` with a resolver that maps each cell's current biome to its fester biome (`fester_variant` entry, else `remission:fester`; `remission:fester` and every variant target map to themselves), marks the chunk unsaved and calls `ChunkMap.resendBiomesForChunks`, the vanilla `/fillbiome` path: players who have the chunk get `ClientboundChunksBiomesPacket`, and the client replaces the biomes, clears the tint caches of the chunk and its neighbours and rebuilds their sections. A player still waiting for the chunk gets the new biomes with it. No Remission payload; `PROTOCOL_VERSION` is unchanged.
- Chunk attachment `remission:festered_stage` (int, saved, server only) records the stage a chunk was brought up to, written only when the cave pass finishes, so queued chunks already there cost one attachment read, and an interrupted chunk is redone (both passes are idempotent) on its next load. Purification (P5.2) lowers it with the chunk's level and clears it after a cleanse, so the stage work festers the chunk again if the Strain returns; chunks a quarantine pylon wards are skipped.
- Blocks: `festering_grass` (`SnowyDirtBlock`: no spreading or decay, in `#minecraft:dirt`, so it also yields festered soil, P7.1), `festering_log` (`RotatedPillarBlock`, in `#minecraft:logs` so leaves around it keep their distance), `festering_leaves` (`LeavesBlock`, in `#minecraft:leaves`, `cutout_mipped`), `festered_stone`, and since P4.6 `festered_deepslate` (`RotatedPillarBlock` with deepslate's properties). Models and textures are untinted; their colour is in the placeholder textures (CONTENT-PROVENANCE).
- Data: `festers_into` (blocks, default grass 1, logs and leaves 2, `#minecraft:stone_ore_replaceables` to festered stone and `#minecraft:deepslate_ore_replaceables` to festered deepslate 3; each entry also has an `underground_stage`, P4.6) and `fester_variant` (biomes, empty by default) are NeoForge data maps registered in `FesterMaps` (`RegisterDataMapTypesEvent`), server side, `/reload`-able. The `remission:fester` biome is datagen (`RemissionBiomeProvider`): no features or carvers, since land flips after generation. Contracts: remission-data-formats ("Festering stages, blocks and the fester biome").
- Gametests: `FesteringStageTests` (own batch): one column at stages 0–3 (cumulative, axis and persistence kept, one event per block, a repeated pass changes nothing); a queued chunk and stage events festered by the ticking work, the biome flipped at every height at the last stage, a re-queued chunk skipped; `fester_variant` resolution, the decoded value shapes, the shipped defaults and a flip into a variant. Whole-chunk tests use a force-loaded chunk 96 chunks east of the test grid and restore its biome.
- Cost (foundry, shared with other lanes, load about 6.5; a throwaway gametest over 40 force-loaded chunks, each a dense forest of 16 trees with 5x3x5 canopies over a stone layer): a whole chunk at stage 3 (every column: grass or stone, 80 logs, about 1,000 leaves) takes 0.49 ms mean, 0.33 ms median, 1.7 ms max, so a tick's 64 columns cost about 0.12 ms; rescanning a chunk with nothing left to change 0.10 ms; the last stage with its biome flip and resend 0.18 ms. Not committed as a benchmark.
- Harness scenes (visual-checks): `world/stages` (one chunk per stage 0–4, levels 0, 10, 30, 60, 90, each with a small tree, a horizontal log and a stone outcrop, set with the harness command `harness fester`; shots `overview`, `stage_0`..`stage_4`; the first shot runs `harness resend` so chunks edited while still being sent get their settled light) and `world/biome_flip` (shots `before`, `after`: a chunk flips while the client has it loaded, through the harness command `harness fester`; `inside`: the fester sky and fog from inside the flipped chunk).

### Cave festering (phase 4, built in P4.6)

- The cave pass in `FesteringStages` runs after a chunk's surface pass on its own budget: `LAYER_BUDGET` (8) block layers (16 by 16 blocks at one height) per `LevelTickEvent.Post` and level, so a full overworld chunk with stone in every section takes about 48 ticks, and a flat or empty one a few. It walks the chunk section by section, bottom to top; a section whose block palette (`PalettedContainer.maybeHas`) holds no block with an entry that festers underground at this stage (and is not already its target) costs one unit and is skipped, so air, ocean and already festered sections cost almost nothing. The stage is the one the surface pass reached, carried with the queued chunk.
- A block festers underground when its `festers_into` entry's `underground_stage` (default `FesterMaps.UNDERGROUND_STAGE`, 3; 0 is off) and `stage` are both at or below the chunk stage, and at least one of its six sides is air (`isAir`: air, cave air, void air). A side in a chunk that is not loaded counts as solid, so nothing loads chunks. Rock without air beside it and blocks without an entry (ores, dirt, gravel, sculk) are left alone; block entities are skipped as on the surface. At or above `FULL_DEPTH_Y` (0) every such block festers; below it one in `SPARSE` (4), picked by `festersBelowFullDepth`: a fastutil `HashCommon.mix` of the block position, so the result depends only on the position, not on world seed, scan order or reloads. Both are constants, not config.
- Replacement and events are the surface pass's: shared state properties kept (deepslate `axis`), flags `UPDATE_CLIENTS | UPDATE_KNOWN_SHAPE`, one `BlockFesteredEvent` per replaced block. Full opaque blocks replace full opaque blocks, so no light changes. The biome flip is unchanged (the surface pass does it at the last stage; it already covers every height).
- Resume: `festered_stage` is written when the cave pass finishes, so a chunk unloaded or parked mid-way is redone from its surface pass when it is back. No new attachment.
- Defaults: P4.2's single `#minecraft:base_stone_overworld` entry became `#minecraft:stone_ore_replaceables` (stone, granite, diorite, andesite) to `festered_stone` and `#minecraft:deepslate_ore_replaceables` (deepslate, tuff) to the new `festered_deepslate`, both stage 3. Tuff now festers into festered deepslate (it matches its colour), and a modded stone that is only in `base_stone_overworld` no longer festers by default; packs add it. Two disjoint tags because a data map file cannot override one block of a tag entry (its values are an unordered map).
- Gametests: `CaveFesteringTests` (batch `cave_festering`, plus `cave_festering_resume` alone): a hollow stone cube with ore, deepslate and tuff in its walls (exposed blocks fester with one event each, the inside and the ore stay, deepslate keeps its axis, a repeated pass changes nothing); the underground stage gate (shipped entries from stage 3, decoded `underground_stage` 1 and 0, never below the entry's `stage`); every vanilla stone's target on the surface and in a cave; a full layer at `FULL_DEPTH_Y` and a sparse one below it, matching the hash and identical when rebuilt; a chunk unloaded while its cave pass runs is not recorded and finishes every section after it loads again. Each uses its own chunk 112 or more chunks east of the test grid.
- Cost (foundry, shared, load about 3.5; a throwaway gametest, not committed, over 12 synthetic chunks of stone above deepslate up to Y=72 with about 1.7% coal ore and 40 carved cave spheres of radius 2–4 each, festered at stage 3): the cave pass takes 0.14–0.17 ms mean, 0.14–0.16 ms median, 0.42–0.44 ms p95 and under 0.5 ms max per tick at 8 layers; a rescan with nothing left to change 0.08–0.09 ms mean; the surface pass in the same chunks 0.07 ms mean. At 16 layers per tick it was 0.30 ms mean, 1.4 ms max, so the budget was halved.
- Harness scene `world/caves` (visual-checks): a carved tunnel under each of five chunks at stages 0–4 (stone with ores in the walls and tuff in the floor), one in deepslate next to sculk above Y=0 at stage 4, and one below Y=0 at stage 4 (sparse); shots `overview`, `stage_0`..`stage_4`, `deepslate_sculk`, `deep_sparse`.

### Festering land atmosphere (phase 4, built in P4.11)

- Biome effects (datagen, `RemissionBiomeProvider`): `remission:fester` keeps P4.2's colours (violet-grey sky `#8F84A3`, mauve fog `#A597B0`, water fog `#2B1F36`) and adds its own ambient loop, cave-style mood sound (every 3000 ticks in dark spots, half vanilla's cave delay), occasional additions (wet, organic noises) and music that replaces whatever plays when a player walks in (`replace_current_music`, 2400–9600 ticks between tracks). Sound events live in `registry/RemissionSounds`; files and subtitles in `assets/remission/sounds.json`. Variant biomes inherit none of it (remission-data-formats).
- Stage fog (`client/FesterFog`): on each client tick the target strength is stage / last stage (stage 2 of 4 is 0.5) times the client option `[atmosphere] festerFog` (0 to 1, default 1); the fog eases toward it over 20 ticks. `ViewportEvent.RenderFog` then pulls the fog planes toward 2 and 40 blocks (terrain) and the sky fog end toward 40 blocks, in proportion, only with no fluid in the camera and no blindness or darkness. Colours stay the biome's.
- **Stage source decision: no new payload.** The scope asked for the stage from state the client already has. ### Surges and miasma clouds (phase 4, built in P4.3)

- One `SurgeController` per server level (`Surges`, ticked on `LevelTickEvent.Post`), its state in `SurgeData` (`data/remission_surges.dat` in the dimension folder: the next due time and the current surge with its players and hosts). At most one surge runs per level. A surge belongs to an origin nidus; its area is that nidus's spread reach (`SpreadSettings.radius()`, Manhattan in chunks, 7 by default).
- Schedule: the first tick sets the next surge due `[surges] intervalTicks` later (default 24000), and the end of each surge sets it again. With `scheduled` on, a due surge starts once a player (alive, not a spectator) is inside some nidus's area, checked every 20 ticks; the origin is picked among those nidi by a hash of the game time. `/remission surge start` (any time, either setting) picks the nearest nidus whose area holds the position.
- Phases: a warning (`warningTicks`, default 600: title and subtitle, the vanilla raid horn, a yellow boss bar counting down for everyone in the area), then the surge itself (`durationTicks`, default 2400: purple boss bar, the horn and an action bar line), ended by its duration, the origin nidus leaving the index, or a stop. No Remission payload: titles, sounds and the boss bar are vanilla packets, so `PROTOCOL_VERSION` is unchanged.
- While it runs: the spread engine multiplies the origin nidus's live steps and its own chunk's growth by `spreadMultiplier * intensity` (`SpreadEngine.Land#surgeFactor`, read per visit) before the spread attempt event, so firebreaks and P4.4 multipliers still apply; catch-up never applies it, and the P4.5 rule (a live pass skips chunks queued for catch-up) is unchanged. Every `WAVE_TICKS` (200), starting when it starts, a wave queues `hostsPerWave * intensity` hosts around each player in the area; the queue spawns at most `HOSTS_PER_TICK` (2) per tick, none on Peaceful and none while `maxHosts` of the surge's hosts are alive and loaded. When it starts it releases `clouds * intensity` (at most 32) miasma clouds.
- Host spots (`SurgeHosts`): a random column 8 to 20 blocks from the player, in a loaded chunk inside the area at festering stage 1 or higher; in it, the spot closest to the player's height within 16 blocks with a sturdy floor, two blocks of room (`NaturalSpawner.isValidEmptySpawnBlock`, the type's spawn box free) and the type's spawn placement. A covered spot (no sky above) also needs the type's spawn rules for an event spawn, so monsters spawn in dark caves and cows and sheep do not; open spots skip the rules, so hosts walk out on festering land by day. A player on the surface gets surface hosts and a player in a cave gets cave hosts. The type is uniform from `#remission:surge_hosts` (default zombie, spider, cow, pig, sheep); the mob is finalised as an event spawn, added, then set to `hostLevel` (default 50, stage 2) through `Corruption.set` with `CorruptionCause.SURGE` (passengers too).
- Survivors: players in the area while it runs (checked every 20 ticks) are caught in it; a player who dies (`LivingDeathEvent`, not cancelled) drops out for good. At the end every caught player still online and alive earns `remission:surge_survived` and `remission:surges_survived` through `QuestProgress`, then `SurgeEndedEvent` is posted. A surge stopped or destroyed during its warning never started and posts neither event.
- Miasma clouds: entity `remission:miasma_cloud` (`MiasmaCloud`, misc category, saved with its chunk, `/summon`-able; fields `Radius`, `Heading`, `Age`, `Lifetime`). Released over a random column of a random loaded festering chunk within 3 chunks of a player in the area (or of the origin), 8 blocks above the ground (`MOTION_BLOCKING`), radius 4 to 6, lifetime 3600 ticks. It drifts 0.04 blocks per tick along its heading, eases toward 8 blocks above the ground beneath it, and stays over festering land: when the next step would leave a loaded chunk at stage 1 or higher it turns right, left or back, and holds still if no way stays over festering land. Its area is its bounding box (radius each way horizontally, 3 blocks tall); players inside it gain viral load (P5.1, below), mobs are unaffected. The client draws it with `MiasmaCloudRenderer`: 18 camera-facing translucent puffs at fixed offsets (no randomness or wall-clock animation), drawn back to front without depth writes, placeholder texture (CONTENT-PROVENANCE). Positions sync through vanilla entity tracking every tick it moves (update interval 1; at most 32 clouds per surge), and the client takes them as they come, without extrapolating, so frozen and stepped harness scenes always show the server's position.
- Gametests: `SurgeTests` (own batch `surges`): a scheduled surge comes due, waits for a player in the area, warns, starts (event, clouds, first-wave hosts with cause `SURGE`), awards the survivor and schedules the next; a player who dies is no survivor; a stop during the warning posts nothing and destroying the nidus ends a running surge; the spread factor on live steps and nidus growth with a cancelled step still held and catch-up unchanged; surface spots and hosts; a dark cave gets monsters on its floor and refuses cows and sheep; clouds released over festering chunks only; a cloud drifts, turns at the edge of festering land without leaving it, keeps its altitude, saves and dissipates; the commands; the default tag and `SURGE`'s place.
- Harness scenes (visual-checks): `world/surge` (shots `land`, `hosts`, `cave`) and `world/miasma_cloud` (shots `side`, `below`, `drift`).
- Cost (foundry, `SpreadBenchmark`, shared with other lanes; P4.3 run): with the surge hook in place the P4.4 cases stay in their ranges (default live spread 1.0 µs mean per tick, max 0.10 ms; stress 30.7 µs mean; `listeners` 33.4 µs; catch-up of 1,024 chunks 32 ticks at 107–115 µs mean, at most 0.25 ms). The `surge` case runs the default case with a surge from one of the 16 nidi: 0.8 µs mean, max 0.22 ms. A whole surge (600-tick warning, 2400-tick surge, four players in the area, default `[surges]`) costs the controller 1.2 µs mean per tick, p99 3.4 µs, at most 1.1 ms in the tick it starts (three clouds and the first two hosts); it ended with 16 hosts (the `maxHosts` cap) and 3 clouds.

The same engine runs in reverse for the Counterstrain (phase 9).

### Nidus encounters (phase 4, built in P4.10)

- While `[nidi] vitality` is above 0 a nidus is fought, not mined (contract and numbers: remission-data-formats, "Nidus encounters"). `NidusBlock` refuses survival mining (`getDestroyProgress` 0, and `onDestroyedByPlayer` refuses any player break but a creative one, so machines acting as fake players cannot mine it either), takes bedrock's explosion resistance through the location-aware `getExplosionResistance`, and turns damage into calls on its block entity: a strike from `attack` (called by `ServerPlayerGameMode` after the left-click event, spawn and claim checks; fake players are ignored there and in the block entity, so a machine can neither mine nor strike it), arrows and tridents from `onProjectileHit`, and explosions from `NidusEncounters`' `ExplosionEvent.Detonate` listener, which looks up loaded nidi within twice the radius through `NidusIndex` (explosions never put a nidus in their block list). The block keeps its registered strength (5, hoe), so plain mining at vitality 0 is unchanged; it is added to `#minecraft:wither_immune` and `#minecraft:dragon_immune`. Creative breaks and edits still remove it at once.
- `NidusBlockEntity` (server ticker) holds the fight: the vitality before the player factor (fixed at the first damage from growth since the index's `since` time and distance from the world spawn), the counted players (raised every 20 ticks when more are within `radius`, scaling the damage taken so its share holds; never lowered), damage taken, thresholds passed, the last damage time and the contributors (UUID to last damage time), all saved under `fight`. `strike(...)` applies the per-player strike cooldown (`strikeCooldownTicks`, kept in a transient map) before it computes the charge-scaled damage and resets attack strength. `damage(...)` does nothing without a real player behind the damage (so hosts, mob blasts and ownerless TNT never start or feed a fight), posts the cancellable `NidusDamagedEvent`, caps projectile and explosion damage at 1 vitality left, credits the player, and passes thresholds; each starts a surge through `SurgeController.startNow` (no warning; a surge already in the level ends `SUPERSEDED`, since one surge runs per level; one from the same nidus awards nothing and hands its caught players and hosts to the new one through `Surge.inherit`, so a fight awards `surge_survived` once) at `round(index × player factor)` and lashes nearby survival players (viral load through `ViralLoad.set` with cause `NIDUS`, knockback, a vanilla sound and particles). After `regenDelayTicks` without damage it regenerates (the boss bar then moves every 10 ticks or by 1%); once whole the fight ends and thresholds re-arm. `NidusSettings.current()` builds the settings once per config load or reload (`ModConfigEvent`), not per call.
- The final blow is a strike that takes the last point: the block entity records the destroyer and the contributors within the window, calls `destroyBlock` with drops, and `NidusBlock.onRemove` passes them through `FesteringLand.nidusRemoved` to `NidusDestroyedEvent`; then `NidusEncounters.credit` fires `remission:nidus_destroyed` and the stat for each online contributor through `QuestProgress` (the location predicate is tested in the nidus's level, wherever the player is). A creative break (or any break at vitality 0) credits the breaker and recent contributors the same way.
- Players see the fight without a Remission payload (`PROTOCOL_VERSION` unchanged): a red `ServerBossEvent` for players within `radius` while it fights, and the block state `NidusBlock.DAMAGE` (0–3, quarters of vitality lost), which the block entity sets as the fight goes and clears when it ends, so every client sees wounds through ordinary block updates (models `nidus_damaged_1` to `_3` from datagen). The vanilla block-crack overlay was tried first and dropped: on the nidus's near-black texture even stage 7 was barely visible in the harness. The client reads `[nidi] vitality` from its own common config only to predict mining progress; the server decides.
- Tests reach the fight without a client: `NidusSettings.override` replaces the config settings for a gametest batch, and `NidusEncounters.addTestPlayer` makes a mock player visible to one nidus only, so tests in a batch running side by side do not count each other's players. Gametests: `NidusEncounterTests` (mining and edits, strikes through the left-click path, arrows and explosions at their fractions and the 1-vitality floor, thresholds with surges and lashes, regeneration and saving, the final blow with contributors inside and outside the window, player scaling and its cap, the damaged event scaling and cancelling, fake players, strike spam against charged swings, player-only attribution with block-breaking blasts and a wither skull, one `surge_survived` per fight, and vitality 0 in its own batch). `NidusFightBenchmark` (registered only with `REMISSION_NIDUS_FIGHT=<trials>`; `REMISSION_NIDUS_FIGHT=3 ./gradlew runGameTestServer` writes `run/gametest/nidus-fight-<trial>.txt`) is the scripted balance fight standing in for a played one, since foundry has no input: a survival player in iron armour with an iron sword against a full-grown nidus on Normal with real threshold surges, hosts and lashes (numbers: remission-data-formats). `QuestTriggerTests` breaks its nidus as a creative player. Harness scene `world/nidus_fight` (visual-checks) and the harness command `harness nidus <pos> <vitality>`.

### Festering land infection (phase 4, built in P4.7)

- `FesteringExposure` runs one `ExposureTracker` per server level on `LevelTickEvent.Post`. Every 20 ticks a pass snapshots the level's mobs (`ServerLevel.getAllEntities()`, `Mob`s only) and checks up to 256 per tick, ending the tick early once 32 have become hosts (`ExposureSettings.INTERVAL_TICKS`, `MOB_BUDGET`, `INFECTION_BUDGET`), so a pass over more mobs, or a herd reaching the threshold together, continues on later ticks. Each checked mob in an entity-ticking chunk gains, if its chunk's Strain level (`CorruptionQueries.chunkLevel`) reaches `[infection] festeringLandMinStage` under `[festering] stageThresholds`, or loses, otherwise, the ticks since the previous pass started. Height does not matter, so caves under a festering chunk count in full; viral load (P5.1) is where height falloff belongs.
- Exposure is the entity attachment `remission:festering_exposure` (int ticks, saved with the mob, skipped at 0, server only). Immune mobs, hosts and mobs whose profile sets `conversion.festering_land` to false have it cleared; the cheap immune and host checks run before the profile lookup, and the land check before both, so mobs outside festering land cost one chunk attachment read.
- At `festeringLandExposureTicks` the exposure is cleared and `Infection.infectFromFesteringLand` turns the mob into a host at the first host stage, in place (not healed) or through its profile's `convert_to`, the same path as infection on kill, with `CorruptionCause.FESTERING_LAND` on `HostCorruptedEvent`. Turning `[infection] festeringLand` off stops the passes and freezes exposure. This is the source that creates the first hosts in normal play.
- `ExposureTracker` takes its settings, mob source and profile lookup as arguments, so tests and the benchmark drive separate trackers over chosen mobs with synthetic game times.
- Gametests: `FesteringInfectionTests` (each test alone in its own batch, in its own chunk, restoring the chunk's land and blocks afterwards; far force-loaded chunks were dropped because generating them under load could outlast the test timeout): mobs on the surface and in a sealed pocket below it become hosts after the exposure time with `FESTERING_LAND` events; immune mobs, hosts and a `conversion.festering_land: false` profile never do; nothing below the minimum stage or with the source off; exposure decays once the mob's land stops festering and survives save and load; `convert_to` replaces the mob; passes spend the check and conversion budgets per tick.
- Cost (foundry, `ExposureBenchmark`, `REMISSION_EXPOSURE_BENCHMARK=1`, shared with other lanes): 400 pigs and sheep without AI in 16 festering chunks, default config, the whole level's entities as the source. Steady exposure: each 1-second pass takes 2 ticks of 117–247 µs (11.8–24.8 µs per tick averaged, 0.24–0.50 ms per second), single ticks up to 1.6 ms once under load. A wave in which all 400 reach the threshold together runs 13 ticks at 0.64–0.73 ms mean, at most 1.2 ms, with the per-tick conversion cap of 32 (`ExposureSettings.INFECTION_BUDGET`); without the cap the same wave spent 4.5–9.2 ms in each of 2 ticks (up to 11.2 ms), since a conversion (attributes, host goals, event, sync) costs about 25–40 µs against well under 1 µs for a check.

### Festering veins and contact infection (phase 4, built in P4.8)

- Block `remission:festering_vein` (`FesteringVeinBlock`): a vanilla `MultifaceBlock` (one boolean property per face, as glow lichen and sculk veins), no collision, replaceable, drops one per face with silk touch only, `mineable/hoe`. It never spreads by itself and is not waterloggable. Model: one flat face rotated per covered face (datagen multipart, `cutout`); the placeholder texture is crimson branches with yellow-green pustules, so it never reads as teal sculk (CONTENT-PROVENANCE).
- Growth (`FesteringVeins` rules, `VeinGrowth` per level, run from `LevelTickEvent.Post`): in a chunk at or above `[festering] veinMinStage` (default 2), each air block gets a face on each side whose neighbour holds a multiface block, is not a vein and not in `#remission:vein_resistant` (empty by default), where `FesteringVeins.selected` picks it: a fastutil `HashCommon.mix` of the position and side against the stage's coverage (15% per stage from the minimum, at most 60%) times a 0–2 weight hashed per 4x4x4 cell, so veins come in patches. The result depends only on blocks, positions and stage (gametest `veinGrowthIsDeterministic`), and a higher stage keeps every face of a lower one. Only air is filled; player builds are covered, never replaced. Flags `UPDATE_CLIENTS | UPDATE_KNOWN_SHAPE`, one `BlockFesteredEvent` per block that gained faces.
- Budget: a chunk load or stage rise queues the chunk; each tick walks up to 8 block layers (`LAYER_BUDGET`) bottom to top, and a section with no air, or all air with only air above, below and beside it, costs one unit. A finished chunk is due again `REVISIT_TICKS` (1200) later while loaded, so new faces (a wall built, a block mined out) are overgrown within about a minute; this is how veins threaten bases. Nothing is saved: an unloaded chunk is redone from its load event, a chunk that only left full status is parked and resumes, and a chunk that loads at a higher stage gets that stage's veins in one pass (catch-up). Frozen ticks (`/tick freeze`) grow nothing, so harness scenes stay still; `harness veins <from> <to>` grows a box at once.
- Contact infection (`Contact`, `ContactTracker`, `ContactInfection`, built like P4.7's tracker): every 10 ticks a pass snapshots the level's mobs and checks up to 64 per tick (32 conversions at most), so a pass over 400 mobs takes 7 ticks. A mob is in contact when a block in `#remission:infectious` (the five festering blocks and the vein) reaches its bounding box grown by 0.001 (on, in or against it; the outline shape counts) or water reaches into its box in a chunk at or above `[infection] festeringLandMinStage`. Contact adds the ticks since the previous pass, no contact subtracts them (attachment `remission:contact_exposure`, saved, server only), and at `[infection] contactTicks` (default 100; 0 is the first pass that sees it) the mob becomes a host through `Infection.infectFromContact`: festering land eligibility, `convert_to`, `CorruptionCause.CONTACT`. Only `Mob`s are checked, so players never take it. `Contact.of(entity)`/`inContact(entity)` is the reusable query for any entity, players included; contact viral load (P5.2) uses it for players. Inside a quarantine pylon's ward contact infects no mob (P5.2). Festering land exposure is unchanged and separate.
- Water's minimum stage reuses `festeringLandMinStage` rather than a new key, so festering water and festering land start infecting at the same stage.
- Gametests: `FesteringVeinTests` (batch `festering_veins` plus `_order` and `_resume`, each in its own chunk 128 or more chunks east): nothing below the minimum stage, the exact face rule with one event per block and a superset one stage up, every solid face of a build (stone, planks on all six sides, glass, cobblestone) but never a resistant block, the same veins at once, top-down, budgeted and from the level's pass after a stage event, a chunk unloaded mid-pass finishing after it loads, nothing while off, silk-touch-only drops. `ContactInfectionTests` (each alone): pigs on festering grass, in a vein and against festered stone become hosts after the contact time with `CONTACT` events while one on stone does not; first touch at 0 and decay; a cod and a squid in water only from the minimum stage, water kept; immune, host, opted-out and player never; off; `convert_to`; the shipped tag and `CONTACT`'s place before `OTHER`.
- Cost (foundry, `VeinBenchmark`, `REMISSION_VEIN_BENCHMARK=1`, run together with `ExposureBenchmark`, load about 5.5; 16 synthetic chunks at stage 4: stone over deepslate to Y=56 with 40 caves each and a plank hut in every fourth, 25,099 vein blocks grown): the cave pass (P4.6, 8 layers per tick) 92.5 µs mean, 411 µs p95, 1.12 ms max per tick, 29 µs mean on a rescan; the vein pass (8 layers per tick) 20 ticks per chunk, 205 µs mean, 380 µs p95, 0.63 ms max on first growth and 64 µs mean, 0.33 ms max on a revisit with nothing to add (the steady cost while festering chunks stay loaded). With 400 mobs (no AI) on the stone top, the contact tracker costs 79 µs mean, 216 µs p95, 0.83 ms max per tick (about 2 µs per mob check, every mob a miss, the most expensive case) against the exposure tracker's (P4.7) 13 µs mean and 0.31 ms max on the same mobs; a contact wave infecting all 400 at once runs 13 ticks at 0.46 ms mean, 0.65 ms max, with the 32-per-tick conversion cap. P4.7's own benchmark in the same run: steady 12.4 µs mean per tick, wave 0.94 ms mean, 2.4 ms max.
- Harness scene `world/veins` (visual-checks): festering terrain (a grass and dirt mound, a stone outcrop, an oak tree), a stone block with a lit tunnel, a plank hut with glass windows and a doorway on a cobblestone floor, and one deepslate wall across a chunk border with vanilla sculk veins on its clean half and festering veins on its festering half; shots `overview`, `terrain`, `cave`, `build`, `build_inside`, `sculk`.

### Public API (built in P4.4, extended by each system item)

`com.cubiecode.remission.api` is the only package other mods and KubeJS bindings may rely on; everything else is internal, including `public` classes in other packages.

- Conventions: events are NeoForge events on `NeoForge.EVENT_BUS`, posted server side on the server thread by the system that owns the state change, after the change is applied, except the cancellable spread attempt, which is posted before. Batched changes (catch-up, bounded stage batches) post one event per chunk, not per block, unless the event is block-scoped. Abstract bases `HostEvent` (a `LivingEvent`) and `FesteringLandEvent` (carries the `ServerLevel`) group them; listeners register for the concrete events.
- Built events: `HostCorruptedEvent` and `HostCleansedEvent` (from `Corruption.set`, with old and new level and stage and a `CorruptionCause`), `ChunkStageChangedEvent` and `NidusDestroyedEvent` (from `SpreadHooks`; P4.10 adds the destroying player and contributors), the cancellable `StrainSpreadAttemptEvent` with a mutable rate multiplier (from `SpreadHooks`, live and catch-up steps), `BlockFesteredEvent` (from `FesteringStages`, per replaced block, P4.2, and from `FesteringVeins`, per block that gained vein faces, P4.8), `SurgeStartedEvent` and `SurgeEndedEvent` (from `SurgeController`; P4.3), `ViralLoadChangedEvent` (from `ViralLoad`; P5.1), `BlockPurifiedEvent` and `ChunkEnteredRemissionEvent` (P5.2), and `RevenantRisenEvent` and `RevenantSlainEvent` (from `Revenants`; P5.3).
- Built queries (`CorruptionQueries`): `isHost`, `hostLevel` and `hostStage` for any entity (both sides), and `chunkLevel`/`levelAt`, `chunkStage`/`stageAt`, `chunkStageFor`, `maxChunkStage` and `isInRemission` (P5.2) for land (server only; loaded chunks only, never loads one), and `viralLoad` for a player (P5.1; a client knows only its own player's).
- P5.2 adds `BlockPurifiedEvent` (from `Cleansing`, per cleansed block or cleared vein, with a `PurificationCause`), `ChunkEnteredRemissionEvent` (from `Purification`, once per chunk purified to level 0) and `CorruptionQueries.isInRemission` (server, loaded chunks; P8.2's remission-zone map layer reads it), plus `CorruptionCause.PURIFICATION` (a handheld purifier used on a host). `ChunkStageChangedEvent` now also fires when purification lowers a chunk's stage.
- Team query (P4.12): `TeamQueries.areTeammates` is the one answer to "are these two players teammates?" for every rule that involves teammates (DESIGN, Teams and multiplayer). It takes UUIDs, so either player may be offline. A player is always their own teammate; for two different players it posts `TeamLookupEvent`, which team sources answer, and with no answer they are not teammates. Answers are cached per unordered pair for `TeamQueries.CACHE_TICKS` (100) server ticks; sources call `TeamQueries.invalidate`/`invalidateAll` when their teams change, and the cache is cleared when the server stops. `integration/ftbteams/FtbTeamsIntegration` (FTB Teams `compileOnly` with FTB Library and Architectury for its API types, `type="optional"` `[2101.1,)`, registered after a `ModList` check) answers from FTB Teams for players it knows, by UUID, and invalidates on FTB Teams' player-changed, team-deleted and manager events. Packs without FTB Teams answer it from KubeJS once P8.3's bindings exist. Gametests: `TeamQueryTests` (no answer, a test listener, the cache and its expiry) and `FtbTeamsTests` (registered through `RegisterGameTestsEvent` only when FTB Teams is loaded: members of one party and of different parties, the cache following a join and a leave).
- Gametests: `PublicApiTests` fires each event and asserts its payload, cancels and scales spread (live and catch-up), and checks the queries for host and non-host entities at every host stage and for every chunk stage.
- Cost (foundry, `SpreadBenchmark`, shared with other lanes, so runs vary by 2x or more): live spread with the events posted and no listeners runs the stress case (64 nidi, a pass every second) at 36–69 µs mean per tick against 32 µs with the hooks stubbed out, and the default case at 0.8–1.2 µs (0.9 before); one listener each on the spread attempt and stage events (`listeners` case) gives 34–89 µs. Catch-up of 1,024 chunks still takes 32 ticks; with the parent-first rule (fix round 1) its ticks cost 51–109 µs mean (default) and 119–537 µs mean, at most 0.92 ms (64 nidi), against 38–75 µs mean and 0.23 ms before. Single ticks up to 3.3 ms (live) appeared once and did not reproduce.
- Schemas, names and firing rules live in remission-data-formats ("Public API events and queries") and change only with the code. KubeJS bindings for them are P8.3.

### Tech chain: machines (phase 7, built in P7.2)

- Three blocks, `remission:analyzer`, `remission:sequencer` and `remission:synthesizer`, are one `MachineBlock` and one `MachineBlockEntity` class parameterised by `MachineKind`, which fixes each machine's input slot count (1, 2, 3) and recipe type (`remission:analyzing`, `remission:sequencing`, `remission:synthesizing`). Every machine has 2 output slots, an input and an output tank (4000 mB) and a 20,000 FE buffer (up to 1,000 FE accepted per call). Constants, not config.
- Recipes: one `MachineRecipe` class (a `Recipe<MachineInput>`, the input slots plus the input tank) with one serializer per type; codecs are NeoForge's flat `SizedIngredient` and `SizedFluidIngredient`, `ItemStack` and `FluidStack`, validated against the machine's slot count. Ingredients are shapeless and match exactly the filled input slots. `isSpecial` keeps them out of the vanilla recipe book. Schema and defaults: remission-data-formats ("Machine recipes").
- Ticking (server only): the block entity looks up a recipe (`RecipeManager.createCheck`, cached) only when its inputs or input tank change, then each tick checks that the outputs have room and the buffer holds that tick's share of the recipe's energy, and advances. A completed craft takes the ingredient counts from the slots the match assigned, drains the fluid ingredient and inserts the results. The recipe in progress is saved by id with its progress, so a reload continues the craft; a recipe that stops matching resets progress.
- Capabilities (`MachineCapabilities`, `RegisterCapabilitiesEvent`): item, fluid and energy handlers, the same on every side, that only insert into inputs and only extract from outputs, so AE2, Mekanism, Create and pipes can run them unattended (DESIGN's "the sequencer reads from the network" is pack-side on these handlers).
- Menu and screen: `MachineMenu` syncs slots through vanilla slot updates and progress, recipe time, energy and both tanks through `ContainerData`; vanilla sends data slots as shorts, so each value is two slots (low and high 16 bits) and fluids are their registry id plus amount. No payload, so `RemissionNetwork.PROTOCOL_VERSION` is unchanged. The menu type needs no extra open data, so spectators, who open menus without it, can look inside. `MachineScreen` draws the energy bar, both tanks (the fluid's still texture, tinted) and the progress arrow, with tooltips; its background is placeholder art (CONTENT-PROVENANCE).
- Recipe viewers: `integration/jei/RemissionJeiPlugin` registers one category per type (ids as the recipe types; catalyst the machine; the screen's arrow is a clickable area). EMI shows them through its JEI compatibility, which calls a category's `draw` but not JEI's recipe-extras widgets, so the arrow and the energy and time line are drawn in `draw`; the arrow is static (an animated one follows wall-clock time and would make harness shots differ). JEI is `compileOnly`, declared `type="optional"` (`[19.51,)`), and only JEI's annotation scan reaches the plugin, so Remission loads without it (checked with `-Pdev_runtime_mods=false`). No native EMI plugin is needed.
- Gametests: `MachineTests` runs each machine's default recipe fed only through the capabilities (analyzer: tissue to miasma and a nidus core to a block scan; sequencer; synthesizer), waits without energy or with too little fluid, holds a craft while the output tank cannot take it, checks the side rules of the item, fluid and energy handlers, save and load of contents, progress continuing after a reload, and the schema rules (slot count, results required, time required; energy adding up over a craft).
- Harness scenes (visual-checks): `tech/machines` (shots `blocks`, `analyzer_gui`, `sequencer_gui`, `synthesizer_gui`: the three machines, then each menu mid-craft) and `tech/recipe_viewer` (shots `analyzing`, `sequencing`, `synthesizing`: each category opened in EMI, or in JEI when EMI is absent, `-Pdev_runtime_emi=false`).

### Tech chain: synthesizer products and KubeJS (phase 7, built in P7.3)

- Products, each a default `remission:synthesizing` recipe from a strain sequence (remission-data-formats, "Synthesizer products"): `remission:serum`, `remission:purifier_fuel` and `remission:counterstrain_prototype`. The P7.2 placeholder `synthesizing/host_tissue` stays as a default.
- Serums: `SerumItem` is drunk like a potion (32 ticks, leaves a glass bottle) and calls `Serums.apply(target, SerumSettings)`: a player loses `[serums] viralLoadDrop` viral load at once (`ViralLoadChangedEvent.Cause.SERUM`), and any living target gets `remission:inoculated` for `inoculationTicks`. P7.6's injector reuses `Serums.apply`, so every dose is the same. `InoculatedEffect` does nothing per tick: `ViralLoad.update` decides gain or decay on the unscaled gain and then multiplies a positive gain by `Serums.gainFactor` (`inoculationFactor`, floored at `SerumSettings.MIN_INOCULATION_FACTOR` 0.1, while the effect lasts, else 1), so every gain source (land, water, clouds, contact) is scaled, an inoculated player in festering land never decays, and inoculation is never immunity. Milk clears it like any other effect (NeoForge's default cures), so it is a buff a player can lose, not a permanent immunity; drinking water still adds its dose.
- Purifier fuel: an item in `#remission:purifier_fuel` (`HandheldPurifierItem.FUEL`). For now its only use is repairing the handheld purifier in an anvil (`isValidRepairItem`); the tag is the fuel contract the reclaimer (P7.4) consumes, and P7.5's variant fuels join it.
- Unstable Counterstrain prototypes: `PrototypeItem` throws a `ThrownPrototype` (a `ThrowableItemProjectile`, drawn with vanilla's `ThrownItemRenderer`, splash potion gravity). Where it lands, `CounterstrainPrototypes.land` either backfires (chance `[prototypes] backfireChance`): it releases one miasma cloud through P4.3's `MiasmaCloud.create` (default radius, 1200 ticks; unchanged cloud code, so it climbs out of reach within a couple of seconds) and, since the cloud alone would cost little, gives every exposed player within `radius` blocks `backfireViralLoad` at once through `ViralLoad.addDose` (`ViralLoadChangedEvent.Cause.PROTOTYPE`); it cleanses nothing; or it cleanses the festered blocks and veins in a cube of `radius` through `Cleansing.cleanseBox` and lowers the chunk by `step` through `Purification.lowerLevel`, both with `PurificationCause.PROTOTYPE`, crediting the thrower if the chunk enters remission. No dispenser behaviour. Phase 9 (P9.1) extends prototypes with variants that resist them.
- KubeJS (no Java dependency, so no `integration/kubejs/`): Remission ships `data/remission/kubejs/recipe_schema/<type>.json` for the three types, which KubeJS 2101 reads from any datapack, so `event.recipes.remission.<type>(results, ingredients[, fluidIngredient])` with `.fluidResult`, `.energy` and `.time` builds recipes, and `event.remove`, `replaceInput` and `replaceOutput` work on them. The schemas' list bounds match each machine's slots. Verified in a dev run with `.agents/skills/kubejs-scripting/examples/remission_machine_recipes.js` (kubejs-scripting).
- Gametests: `SerumTests` (a dose lowers viral load with its cause and inoculates, the bottle comes back, inoculation halves gain and milk clears it; fuel repairs the purifier; a prototype cleanses its radius and lowers its chunk into remission with the thrower credited, backfires into a miasma cloud and doses nearby exposed players, and lands when thrown; inoculation has a floor and never lets an exposed player decay; the synthesizer makes each product from its default recipe; the KubeJS schemas name the recipe fields and slot limits).
- Harness scene (visual-checks): `tech/serums` (shots `items`, `thrown`, `effect_hud`, `effect_inventory`).

### Viral load (phase 5, built in P5.1)

- Player attachment `remission:viral_load` (`ViralLoadState`: a float 0–100 and the trend of the last update). The load is saved with the player (not at 0); the trend is not; nothing is copied on death, so a respawned player starts at 0. Field contract and config: remission-data-formats ("Viral load").
- `ViralLoad` runs on `PlayerTickEvent.Post` every 20 ticks (`ViralLoadSettings.INTERVAL_TICKS`) for each server player, skipped while the level's tick rate manager is frozen (`/tick freeze` keeps viral load, which also keeps harness HUD shots fixed). An update sums the gain per minute where the player is: `[viral_load] landGain` for the chunk's festering stage (`CorruptionQueries.stageAt`) times the altitude factor, `waterGain` when the feet or eyes are in water in festering land, `cloudGain` inside a miasma cloud, and since P5.2 `contactGain` while `Contact.of(player)` (P4.8) finds an infectious block on, in or against the player, anywhere (`contact` turns it off; `Kind.WATER` adds nothing, since `waterGain` already covers festering water); with no gain it applies `decay`. Players in creative or spectator, dead players and fake players gain nothing. `LivingEntityUseItemEvent.Finish` adds `drinkDose` for a water bottle drunk in festering land (bottle origin is not tracked; P10.6 owns contaminated items).
- Altitude: the height above the ground is feet Y minus `MOTION_BLOCKING_NO_LEAVES` at the player's column. Anything at or below `falloffStart` gains in full, which covers standing on the ground, water at the surface, caves, tunnels and bases below a festering chunk, and anywhere under a roof; above it the factor eases to `falloffMinimum` at `falloffEnd` along `falloffCurve` (`LINEAR`, `QUADRATIC`, `SMOOTH`). Airborne players, elytra and vehicles above festering land therefore avoid most of the gain. A player's own builds count as ground, so standing on a tower in festering land gains in full; Create Aeronautics airships are not part of the heightmap.
- Miasma clouds: the player's bounding box against each cloud's bounding box, searched over the player's box grown by the largest cloud radius (`MiasmaCloud.MAX_RADIUS`) and height, since a cloud's centre can sit in another entity section than the player. Clouds affect players only; mobs have festering land infection (P4.7).
- Debuffs: after the change, each `debuffs` entry whose viral load is reached applies its vanilla effect (highest amplifier per effect) for 240 ticks, ambient and without particles, refreshed every update (above 200 so the effect icon does not blink); at `damageAt` the player takes `damage` per second of damage type `remission:viral_load` (bypasses armour; death message "succumbed to the Strain"), so P5.3 can recognise viral load deaths.
- **Sync decision: a custom payload**, not attachment sync. `ViralLoadPayload` (`remission:viral_load`: float load, var-int trend) goes only to the player it belongs to, when the state changes (at most once per update or drink) and on login, respawn and dimension change. Attachment sync would also send the value to every client that starts tracking the player (P6.2 found the initial sync ignores the predicate) and offers no place for the trend. Its client handler only sets the attachment on the local player, so common code references no client class. Adding it bumped `RemissionNetwork.PROTOCOL_VERSION` to 2.
- API: `ViralLoadChangedEvent` (old and new load, cause `EXPOSURE`, `DRINK`, `DECAY` or `OTHER`) after each change of the load, and `CorruptionQueries.viralLoad(Player)`. Trigger `remission:viral_load_changed` (`viral_load` float range) fires at the same moments; no stat.
- HUD: `ViralLoadHud` registers GUI layer `remission:viral_load` above `minecraft:air_level` and draws one row at `Gui.rightHeight` (so above the hunger bar and air bubbles, and other mods' rows stack above it): the placeholder icon sprite `hud/viral_load` (CONTENT-PROVENANCE), a 70-pixel bar drawn in code whose colour steps every quarter (pale green, yellow, orange, Strain violet), and a chevron while rising or falling. Hidden at 0, outside survival and adventure, with the GUI hidden, or with client config `hud.showViralLoad` off.
- Gametests: `ViralLoadTests` (each test alone in its own batch with players never added to the level, driving `ViralLoad.update` with explicit settings): land gain by stage and the cap, contact gain on, in and against an infectious block, off, and added to land gain, and no extra gain from festering water (P5.2), swimming in festering water and not in clean water, drinking (water only, festering land only, not in creative), miasma clouds including a wide one centred more than a section away, the altitude factor at several heights with the falloff on and off and the three curves, full gain in a cave and under a roof, decay to 0 and the disabled freeze, debuffs escalating with their flags and the damage type, and the trigger, query, save and load, and death reset.
- Harness scene `survival/hud` (visual-checks): a survival player on stage 3 festering land, shots `none` (no meter at 0), `rising` (20), `falling` (85), `full` (100), `scale_2` and `scale_3` (60 at GUI scales 2 and 3). It introduced the shot fields `hud` and `gui_scale` and the harness command `harness viral_load`.

### Purification and remission zones (phase 5, built in P5.2)

- **Lowering land:** `Purification.lowerLevel(level, chunk, amount, cause, player)` is the one path that lowers a chunk's Strain level. It writes the level through `FesteringLand.setChunkLevel` (stamped with the game time, posting `ChunkStageChangedEvent` when the stage moves), lowers `festered_stage` to the new stage (so the stage work festers the chunk again if the Strain comes back), and at 0 puts the chunk **in remission**: chunk attachment `remission:chunk_remission` (the game time it entered, saved, server only), a queued full cleanse, `ChunkEnteredRemissionEvent`, and credit for nearby players (below). A chunk leaves remission when anything raises its level again (`ServerLand.set`, `setChunkLevel`); there is no leave event. While it is in remission and level 0, catch-up counts its missed passes from the remission time, not from before it was purified (`ServerLand.get`), so a reload does not undo a purification.
- **Cleansing** (`Cleansing`): a block with a `remission:cleanses_into` entry (NeoForge data map, server side, `/reload`-able; defaults festering grass to grass, festering log to oak log, festering leaves to oak leaves, festered stone to stone, festered deepslate to deepslate) is replaced by its target with shared state properties kept (axis, snowy, leaf distance and persistence); a festering vein is cleared to air; blocks with block entities are never touched. Flags `UPDATE_CLIENTS | UPDATE_KNOWN_SHAPE`, one `BlockPurifiedEvent` per changed block. Which block festered is not recorded, so a festered birch log cleanses into an oak log and festered tuff into deepslate. A whole-chunk cleanse ends by restoring every fester biome cell (`remission:fester` or a `fester_variant` target) to what the level's biome source generates there, resent through `ChunkMap.resendBiomesForChunks` as the flip is, and by clearing `festered_stage`.
- **Quarantine pylon** (`remission:quarantine_pylon`, `QuarantinePylonBlock` with a data-less block entity that re-indexes structure-placed pylons on load, pickaxe, light 10, pistons cannot move it): `PylonIndex` (`data/remission_pylons.dat` per dimension) keeps every pylon; its **ward** is every chunk within `[purification] pylonRadius` chunks of the pylon's chunk in a square (5 by 5 by default). Inside a ward: the spread engine gives a chunk nothing, live or in catch-up, nidus chunk included (`SpreadEngine.Land.warded`), and steps past it hold once its level falls below the threshold; the festering stage work, the cave pass and vein growth skip it (checked when a chunk starts and on every budgeted step); contact infection does not count (P4.8's tracker treats a warded mob as out of contact). Placing a pylon queues every loaded chunk of its ward for a cleanse, and a warded chunk is queued again when it loads; removing one queues the chunks it no longer wards for the stage work and vein growth, which catch them up to their current stage. Festering land exposure (P4.7) and land viral load are not stopped by the ward; they stop as the warded land drains.
- **Pylon pass** (`PurificationEngine`, one per server level, `LevelTickEvent.Post`, not while ticks are frozen): at each multiple of `[purification] intervalTicks` (200) of game time, every loaded warded chunk (each once, however many wards overlap, in `ChunkPos` key order) loses `pylonStep` (5), so a stage 4 chunk (level 100) is in remission in 20 passes, about 3 minutes 20 seconds. One attachment read per warded chunk; not budgeted. Pylons whose loaded block is gone are dropped first.
- **Chunk cleanse** (`PurificationEngine`): chunks are queued when a pylon starts warding them, when a warded chunk or a chunk in remission loads, and when a chunk enters remission; each tick walks up to 8 block layers (`Purification.LAYER_BUDGET`) bottom to top, and a section whose palette holds nothing to cleanse costs one unit, so a clean chunk costs about 3 ticks of a few microseconds. Nothing is saved: a chunk that unloads mid-way is redone from its load event.
- **Handheld purifier** (`remission:handheld_purifier`, `HandheldPurifierItem`, 256 uses, 10-tick cooldown): used on a block it cleanses every festered block and vein in the cube `purifierRadius` (2) around it and lowers the block's chunk by `purifierStep` (1), crediting the player on the remission event; used on a host it lowers the host's Strain level by `purifierHostStep` (34, about one host stage) with `CorruptionCause.PURIFICATION`. A use that changes nothing costs no durability.
- **Mendroot** (`remission:mendroot`, `MendrootBlock`, a `BushBlock` on dirt, grass, farmland and festering grass, placed by its block item, so any block placer can plant it): on placement it schedules a tick (saved with the chunk); every `mendrootIntervalTicks` (600) it cleanses the cube `mendrootRadius` (3) around it and lowers its chunk by `mendrootStep` (1).
- **Remission zones** (`RemissionZones`, `[remission_zones]`, read when each fires): `spawnSafety` (natural monster spawns fail in chunks in remission, `MobSpawnEvent.PositionCheck`; spawners, events and surges are unaffected), `growthChance` (a crop growth attempt that would fail succeeds with this chance, `CropGrowEvent.Pre`), `yieldChance` (a block in `#remission:remission_yields`, default `#minecraft:crops`, broken in remission drops one more of each item with this chance, `BlockDropsEvent`).
- **Quest progress:** when a chunk enters remission, every living, non-spectator player in the level within 8 chunks (`QuestProgress.REMISSION_CREDIT_RADIUS`, Chebyshev) gains the `remission:chunks_cleansed` stat and fires `remission:region_cleansed`, whose conditions measure the square of loaded chunks of their own `radius` around the player's chunk: `share` (in remission over in remission or festering) and `chunks` (in remission).
- No payload: blocks and biomes reach clients as ordinary updates; `RemissionNetwork.PROTOCOL_VERSION` is unchanged.
- Gametests: `PurificationTests` (each alone in its own batch, in chunks 176 or more east of the test grid): the ward's square radius and a pass draining warded chunks once however many wards overlap; spread, nidus growth and catch-up held in a ward while an unwarded neighbour spreads, and no festering or veins in a ward while the unwarded chunk grows veins; contact infection held in a ward and resuming once the pylon is gone; the ward cleanse (every default block with its properties, a vein, the biome restored, `festered_stage` cleared, one event per block, the outside untouched); remission entry (events, stage event to 0, query, stat for a near and not a far player, `region_cleansed` share and chunk conditions, leaving remission); catch-up from the remission time; the handheld purifier (radius, vein, level, durability, cooldown, remission event with the player, nothing to do, a host with `PURIFICATION`); mendroot (soil, scheduled cleanse, radius, level); spawn safety, the yield bonus and the shipped `cleanses_into` and yield tag. `ViralLoadTests` covers contact viral load.
- Harness scene `purification/pylon_radius` (visual-checks): festering land at stage 4 with veins over four chunks, a pylon placed in the clean chunk east of them; shots `before`, `after` (the pylon placed and `harness purify` run), `border` (the ward's edge between a cleansed and a festering chunk) and `pylon`.

### Revenants (phase 5, built in P5.3)

- **Which deaths:** `Revenants` notes a player's Strain death on `LivingDeathEvent` at `LOWEST` (killer a host or revenant, by the damage's responsible entity or the kill credit; damage type `remission:viral_load`; or the player in a chunk at festering stage 1 or higher, at any height), unless `keepInventory` is on. In the same call stack it takes the experience drop (`LivingExperienceDropEvent`) and the item drops (`LivingDropsEvent`, receiving cancelled events) at `LOWEST`, cancels both and raises a revenant with them. Taking the drop list rather than reading the inventory means the revenant holds exactly what the death would have dropped, after vanishing curses, other mods' additions and drop rules: Curios adds its slot items to the same event at `HIGHEST`, so no Curios code is needed for them. A grave mod that cancelled the drops first keeps them; the experience is then dropped as vanilla would. The drops are cancelled only after the revenant joined the level (`addFreshEntity` returned true); a refused join leaves the drops alone, awards the experience back and indexes and posts nothing. The pending death is keyed to its game tick, and a cancelled or non-Strain `LivingDeathEvent` clears it, so a death some listener cancelled cannot leak into the player's next one. Below the world the revenant rises on the column's surface, over an empty column on the End platform, at the world spawn in the overworld, or just above the minimum height elsewhere, where it hovers when returned home (`Revenants.riseSpot`).
- **Entity** `remission:revenant` (`Revenant extends Monster`): a host in its own type, because it carries a player's items and skin (DESIGN keeps hosts as state for every other mob). Its owner UUID and name are `SynchedEntityData`, so the client can draw the skin without a payload; `PROTOCOL_VERSION` is unchanged. Host goals, attributes, overlay and infection on kill come from the host systems: `Corruption.set` with `CorruptionCause.REVENANT`, at the player's viral load at death (at least the first host level). Equipment slots hold display copies of the player's worn armour and main-hand item (drop chance 0); the held stacks are a separate list, saved with the entity and dropped in `dropEquipment`, which runs whatever the loot game rules say, and its loot table never rolls, so the drop is exactly the held stacks. Persistence: `removeWhenFarAway` false, persistent, kept on Peaceful, no dimension change. Damage: `isInvulnerableTo` lets through only damage whose responsible entity is a player and `minecraft:generic_kill`. Void: `onBelowWorld` puts it back home. Leash: vanilla home restriction (radius 8) with `MoveTowardsRestrictionGoal`, plus `customServerAiStep` dropping targets more than 12 blocks from home and putting it back home beyond 16.
- **Pickup:** dropped stacks carry the `remission:revenant_drop` attachment and vanilla's never-pickup delay (mobs skip them and they never merge) and unlimited lifetime. `ItemEntityPickupEvent.Pre` answers `TRUE` (NeoForge then skips the pickup delay) for the owner and the owner's teammates (`TeamQueries.areTeammates(picker, owner)`, P4.12; the owner may be offline), `FALSE` otherwise, until the timeout; an `EntityTickEvent.Post` check every 20 item ticks, or the next touch, frees an expired item (attachment removed, delay cleared, vanilla extended lifetime). Game times, so time unloaded counts. Hoppers take item entities without any event and are not blocked.
- **Index:** `RevenantIndex`, `SavedData` per level: revenant UUID to owner, owner name and last block position. The revenant writes it on rise and whenever its block position changes, and removes its entry when removed for good (`RemovalReason.shouldDestroy`: killed or discarded), not when unloaded. Nothing else removes entries, so a revenant lost without its removal path (its chunk deleted or regenerated outside the game) leaves a stale entry; P5.4 reads the index to show unloaded revenants and must tolerate stale ones. No reconciliation is done.
- **Reclaim:** when a revenant with an owner dies to its owner or one of the owner's teammates (the team query), `QuestProgress.revenantReclaimed` fires `remission:revenant_reclaimed` (`own` condition) and counts `remission:revenants_reclaimed`; then `RevenantSlainEvent` is posted. `RevenantRisenEvent` is posted after the rise.
- **Client:** `RevenantRenderer` (`HumanoidMobRenderer` with the player model; armour, held item, head, elytra and arrow layers) draws the owner's skin: from the client's player list when the owner is online, else fetched once per UUID through `SkullBlockEntity.fetchGameProfile` and the skin manager, as player heads are, else the default skin for the UUID. It swaps between the wide and slim player models per skin. The host overlay and armour overlay companions reach it through `AddLayers` like any living-entity renderer. No new textures.
- **Teams:** the team query (P4.12) decides who besides the owner may collect; Remission answers it from FTB Teams through `integration/ftbteams/` when FTB Teams is loaded (Counterstrain ships it); other packs answer `TeamLookupEvent`. Revenants need no pack script.
- **Optional Curios** (`integration/curios/`): `compileOnly` and a dev `localRuntime` mod, declared `type="optional"` (`[9,)`). Only gametests call it (to give a test player a slot); see above for why revenants need no Curios hook.
- Gametests: `RevenantTests` (each test alone in its own batch): a revenant refused by a join listener leaves vanilla drops and experience, no index entry and no risen event; a cancelled Strain death does not turn the next death into a revenant; the rise spot below the world (column surface, End platform); a host's kill and a revenant's kill raise one with exactly the dropped items, worn copies and experience, the host state and the risen event; viral load damage (stage from the viral load) and a fall deep under a stage 1 chunk do too, a fall in clean land does not; a non-host's kill drops as vanilla; `keepInventory` keeps everything; a Curios ring goes into the revenant (with Curios loaded; it passes trivially without); only players and `/kill` hurt it; it returns from the void; save and load keeps owner, home, contents, gear and level, unload keeps the index entry, Peaceful keeps it; the leash (driven tick by tick); owner-only pickup with the delay, the stranger's kill not reclaiming and the owner's firing the trigger and stat; a test team lookup listener making a teammate who collects and reclaims (`own: false`); the timeout freeing items on touch and on tick; the index on rise, move and death.
- Harness scene `survival/revenant` (visual-checks): two revenants of the local player in iron and gold armour with a diamond sword, at stages 1 and 3 (raised through `harness revenant`, which runs the rise code); shots `lineup`, `stage_1`, `stage_3`.

### Quest-fired events and map overlay (phase 8, built in P8.2)

- Commands for quests and scripts (`commands/NidusCommands`, `commands/RegionCommands`; syntax and errors in remission-data-formats): `/remission nidus seed <pos>` places a nidus, which indexes itself as any placed nidus does; `/remission region advance <pos> <radius> [stages]` raises loaded chunks within a Manhattan radius by whole festering stages through `FesteringLand.setChunkLevel`, which writes the chunk attachment the way a spread step does and posts `ChunkStageChangedEvent` on a stage change, so the budgeted stage work, veins and map overlays follow. Neither loads a chunk. With P4.3's `/remission surge start` they are the quest-fired events. FTB Quests command rewards fire them (verified in a dev run with a stat task and four auto-claimed command rewards; ftb-quests-authoring).
- **Sync decision: a custom payload** for map overlays, not attachment sync (the `chunk_corruption` attachment stays server only, so clients never get Strain levels they have no use for) and not JourneyMap's server-side overlay API (it needs JourneyMap on the server; most players run it client-only). `FesteringMapPayload` (`remission:festering_map`) carries chunk states for one dimension: the festering stage, and a bit for remission (P5.2's `remission:chunk_remission`); `FesteringMapSync` sends a chunk's state, clean land included, with the chunk (`ChunkWatchEvent.Sent`) and on each stage change or entry into remission (`ChunkStageChangedEvent`, `ChunkEnteredRemissionEvent`) to the players watching it, batched once per server tick. Every client gets it, whether or not it runs a map mod; it costs 9 bytes per chunk sent. Adding it bumped `RemissionNetwork.PROTOCOL_VERSION` to 3.
- Client: `network/FesteringMapCache` keeps every chunk seen festering or in remission this session per dimension (not only loaded ones, so the map keeps showing land the player has left) while a map integration has enabled it, tells listeners about each change and clears on logout. It sits in common code beside the payload whose handler fills it and uses no client-only classes, so no common class reaches into `client/`.
- JourneyMap (`integration/journeymap/`, `compileOnly` API 2.0.0 from maven.blamejared.com, the version JourneyMap 6.0.9 bundles): `RemissionClient` calls `JourneyMapIntegration.init()` only when `ModList` reports JourneyMap; `RemissionJourneyMapPlugin` (`@JourneyMapPlugin`, an `IClientPlugin`) hands over the client API. `JourneyMapIntegration` updates its `MapLayer`s on client ticks; later map features (P5.4's revenants) add a layer there. `FesteringOverlay` draws one translucent `PolygonOverlay` per festering stage and JourneyMap region (32 by 32 chunks), on the full-screen map, minimap and web map, coloured pale ochre, amber, crimson and the Strain's violet for stages 1 to 4, with the hover title `map.remission.festering`, and one in pale cyan for remission zones (`map.remission.remission_zone`). A change re-outlines only its kind and region groups, at most 4 per client tick; `ChunkOutlines` merges chunks into row runs and rectangles before the area union, so an outline costs a few rectangles. Without JourneyMap nothing is stored or drawn.
- Gametests: `QuestEventTests` (batch `quest_events`): seeding (placed and indexed, a nidus, chest or bedrock already there, an unloaded position), advancing (Manhattan reach, adding stages, the cap, the largest `stages` value, one stage event per change, unloaded chunks skipped and never loaded), the payload's wire format and protocol version, sent chunks' states (festering, clean, in remission) reaching only their player on the next tick, a stage change and an entry into remission reaching a player the chunk map tracks for the chunk and no other, and the client cache's change reports.
- Harness scene `quest/map_overlay` (visual-checks): JourneyMap's full-screen map over superflat land with a pond, a path and a stone block, before and after shot commands advance rings of chunks around a nidus to stages 1–4, a second patch to stage 2 and a third that a quarantine pylon then purifies into a remission zone. It added the shot field `map` and the harness command `harness fester <from> <to>`.

### Countermeasures (phase 5, built in P5.7)

- **Hazards** are plain resource locations with no registry, so integrations add their own without Remission knowing them. `StrainHazards` (API) is the one query every hazard asks: `applies(player, hazard)` for a player hazard, `appliesAtBlock(level, pos, placer, hazard)` for a block hazard. Built: `remission:contact` (P5.2's contact viral load: `ViralLoad.gainPerMinute` adds `contactGain` only when it applies). Reserved for later items: `remission:shedding` (P5.6), `remission:fouling` and `remission:rot` (P7.7), `remission:containment` (P7.8), `remission:contamination` (P10.6). Danger never asks.
- **Held countermeasures:** player attachment `remission:countermeasures` (`CountermeasureSet`, a sorted set of hazard ids), saved (not when empty), copied on death and synced through NeoForge attachment sync to its owner (updates only; the initial tracking sync ignores the predicate, as for the bestiary, and nothing on a client reads another player's set). No payload: `RemissionNetwork.PROTOCOL_VERSION` is unchanged. `Countermeasures` is the only writer and mirrors every change into `CountermeasureRecords` (`data/remission_countermeasures.dat` in the overworld), so a placer's team can be asked about while all of it is offline.
- **Team sharing** (DESIGN, Teams and multiplayer), through the team query (P4.12): a grant reaches the player's online teammates (event cause `TEAM`); a player pools theirs with their online teammates' on login and when their team changes, both ways. Team changes are noticed through `TeamQueries.invalidate` / `invalidateAll` (which team sources already call; FTB Teams does) and shared on the next server tick. A team holds a countermeasure when any recorded teammate (online or not) holds it. Revoking takes it from the whole team: the attachments of the player and their online teammates, and the records of offline teammates, each of whom gets a pending revocation (kept in the saved data) that strips it from their attachment at their next login unless the team holds it again by then, so a login never pools a revoked countermeasure back.
- **Hazard query:** false when the player holds the countermeasure or their team does; otherwise the cancellable `StrainHazardEvent` decides, so a listener can hold a hazard back (a pack's stage) but never force one past a countermeasure (it is not even asked). Block hazards first apply the presence rule of `[countermeasures] blockHazards` (`TEAM_ONLINE` default: a player of the placer's team online; `PLAYER_NEARBY`: one in the block's level within 128 blocks, `Countermeasures.NEARBY_RADIUS`; `ALWAYS`), with a block of unknown placer treated as `PLAYER_NEARBY` for any player, whose team then stands in for the placer's. Placers are recorded by the block hazard items (P7.7, P7.8), not here.
- **Protocol:** item `remission:countermeasure_protocol` (`CountermeasureProtocolItem`) with data component `remission:hazard` (a hazard id). Using it grants the countermeasure (cause `PROTOCOL`) and uses one up; a countermeasure the team already holds (offline members included) or a protocol without the component does nothing. Default synthesizer recipes `remission:synthesizing/countermeasure_protocol_<hazard path>`, one per built Remission hazard (`contact`: strain sequence, festered soil, paper, 1000 mB miasma, 8000 FE, 400 ticks); later hazard items add theirs in `RemissionRecipeProvider.countermeasureProtocols`. The contact protocol is listed in the Tools and Utilities creative tab.
- **Quest progress and commands:** each player who gains one posts `CountermeasureGrantedEvent` (cause `PROTOCOL`, `TEAM`, `COMMAND`, `OTHER`), fires `remission:countermeasure_gained` (`hazard` condition) and counts `remission:countermeasures_gained`. `/remission countermeasure grant|revoke|list` (`CountermeasureCommands`).
- Gametests: `CountermeasureTests`: contact viral load stops for a holder and not for another player; a protocol grants and is used up once, a held or blank one does nothing, nor one an offline teammate holds; a grant reaches online teammates and not strangers or offline teammates, a teammate logging in later and a player joining a team pool both ways, revoke reaches the online team and offline teammates (the hazard applies again at once, and their later login neither restores it nor drops one the team gained again meanwhile); the event holds a hazard back and is not asked for a holder; every `blockHazards` mode, no-placer blocks, team countermeasures from the records while the team is offline, and the block event's fields; save and load, owner-only sync, the wire format and copy on death; the command, trigger and stat; the synthesizer making each default protocol.
- Harness scene `research/countermeasure_protocol` (visual-checks): the contact protocol in an item frame and in the hotbar (`items`), and its tooltip in the survival inventory (`tooltip`). It added the shot field `tooltip`.

### Dispersal payload (phase 9)

The Counterstrain is deployed from a dispersal source: a position, radius and rate, ticked by whatever holds it. `remission:dispersal_payload` (a placed block) is the only holder Remission needs to finish the game (P9.2). The source API must not assume a block, so `integration/create/` (P10.6) can tick it from a moving Create contraption, Aeronautics airships included.

## Runtime and test infrastructure

- Run configs: `client` (`run/client`; also loads the dev-only scene harness), `server` (`run/server`), `gameTestServer` (`run/gametest`, exits on completion), `data` (`run/data`, writes `src/generated/resources`).
- Dev runtime mods (`localRuntime`, never published): KubeJS + Rhino + Better Advanced Tooltips, ProbeJS, Architectury, FTB Library/Teams/Quests (FTB Maven, not on Modrinth), JEI + EMI, Mekanism, AE2 + GuideME, JourneyMap, Curios. Toggle `dev_runtime_mods`; `dev_runtime_emi=false` keeps JEI but drops EMI, to check JEI's own screens (P7.2). CI disables them.
- Headless client: `tools/run-client-headless.sh` (Xvfb + VirtualGL EGL on the RTX 4070).
- GPU workflow: `gpu-smoke.yml` (manual dispatch or the `gpu-smoke` PR label, self-hosted foundry runner) runs `tools/run-scenes.sh`, which runs every harness scene through the headless client and compares their screenshots with `tools/compare-screenshots.sh`, then uploads logs, screenshots and diffs.
- Scene harness (dev only): the `harness` source set (`mod/src/harness/`) is a separate client-only mod, `remission_harness`, that only the `client` run loads (`loadedMods`); the jar and the other runs never contain it, and `build` compiles it so it cannot rot. It does nothing unless `-Dremission.harness.scene=<id>` is set (`tools/run-client-headless.sh --scene <id>` sets it; several IDs, comma-separated, run in one session). Then for each scene it recreates a fixed superflat world, runs the scene JSON from `mod/src/harness/resources/harness/scenes/` and saves the named screenshots, leaving to the title screen between scenes, and exits after the last. See the visual-checks skill for the scene format.

## Decisions

- **Gradle 9.8.1** wrapper instead of the MDK's 9.2.1: current at scaffold time, builds with no deprecation warnings.
- **Modrinth Maven pins by version ID** where a project reuses a version number across loaders (JEI resolved to its Fabric jar by number).
- **FTB mods from FTB Maven / CurseForge:** FTB Quests, Library and Teams are not on Modrinth. The pack adds them with `packwiz cf add`.
- **Distribution:** Remission publishes to Modrinth and CurseForge; Counterstrain is CurseForge-first, and its CurseForge zip is the release artifact (DESIGN, Distribution). A Modrinth `.mrpack` cannot download CurseForge files, and the pack already needs CurseForge-only mods. `packwiz curseforge export` lists only CurseForge-sourced mods in `manifest.json` and embeds every other jar under `overrides/mods/`. That is why pack mods are sourced from CurseForge; P10.1 re-sources the current Modrinth-sourced ones. The `.mrpack` export is for local testing only.
- **EMI + JEI together:** EMI is the recipe viewer players see; it takes over JEI's runtime UI (its built-in JEI compatibility) and shows every mod's JEI plugin recipes. JEI stays installed so mods with only JEI plugins keep working. Remission's recipe viewer integration (built in P7.2) is a JEI plugin, which reaches both; a native EMI plugin is added only for EMI-specific features. EMI's JEI compatibility draws a category's `draw` output but not JEI's recipe-extras widgets, so plugins draw arrows and text there.
- **JourneyMap for maps:** chosen over Xaero's (closed source, no overlay API) and FTB Chunks (icon-only API: chunk colouring would work on the full-screen map but not on the zoomed or rotated minimap). JourneyMap's API (`info.journeymap:journeymap-api-neoforge:2.0.0-1.21.1` from maven.blamejared.com, `compileOnly`) has `PolygonOverlay` on the full-screen map, minimap and web map, `PolygonHelper`/`MapPolygonWithHoles` to merge chunks into outlines with remission-zone holes, and a server-side overlay API. P8.2 built the festering and remission-zone overlay on it as an optional client integration in `integration/journeymap/` (Quest-fired events and map overlay, above); P5.4's revenant markers will join it.
- **No climate mods:** Tough As Nails and Cold Sweat are out; viral load is the only exposure system.
- **Integrations pack-side first:** each tie-in in DESIGN's Pack integrations table is pack-side (KubeJS, datapacks on Remission's surfaces) unless the other mod's content can be registered or hooked only from Java; then it is a guarded `integration/<modid>/` package. P10.1 owns membership (`pack/mods/`) and the `compileOnly`/dev-runtime entries for every mod-side integration, so later phase 10 lanes do not touch build files.
- **Content provenance:** player-facing content is tracked in [CONTENT-PROVENANCE](CONTENT-PROVENANCE.md); `tools/check-provenance.sh` (CI: `docs.yml`) fails when an image, sound or model has no row, and when a texture's magenta placeholder marker disagrees with its row's status. `tools/content-editor.sh` replaces content and updates rows without hand-editing files (DEV-ENVIRONMENT, "Content editor").
- **Pack datapack in the pack's `kubejs/data/`:** KubeJS loads it as a datapack in every world without another mod. Every file under it is read as a datapack resource, so it holds only lowercase datapack paths (no READMEs; KubeJS reports an uppercase name as a startup error).
- **Scene harness determinism and exit:** scenes freeze the tick (`/tick freeze`) after time and weather (players keep ticking, so the harness pins the local player's `tickCount` while shooting), stop atlas texture animations at their first frame before the first shot (they advance with client ticks; since P4.6, for sculk in `world/caves`), spawn mobs without `finalizeSpawn` (no random gear or variants), and pin the image-affecting options in memory (GUI hidden, clouds off, render distance 8, FOV 70, fancy graphics). Repeated runs give byte-identical PNGs on foundry. The harness ends the process with libc `_exit` after flushing logs, because under VirtualGL's EGL back end the NVIDIA driver segfaults in `libEGL_nvidia` during libc `exit()`: a normal quit, `System.exit` and `Runtime.halt` all end with exit code 134.
- **Biome flip uses vanilla's resend:** the flip rewrites the chunk's biome containers with `fillBiomesFromNoise` and resends them with `ChunkMap.resendBiomesForChunks` (`ClientboundChunksBiomesPacket`), as `/fillbiome` does, instead of a Remission payload or a full chunk resend, so `RemissionNetwork` stays payload-free and the client's own handler refreshes tints and sections. P4.2 checked it against a lighting difference in `world/stages` (a canopy shadow missing in some runs): sky light probes showed correct light on the server and stale light on the client for chunks the harness edited while they were still pending send, flipped or not (vanilla sends no light update for a chunk pending send). That is a harness timing effect, handled by `harness resend` (visual-checks), not a flip artefact; a full chunk resend made it worse, not better.
- **Festering transformations are data maps:** `festers_into` (blocks) and `fester_variant` (biomes) use NeoForge data maps rather than tags per target or a datapack registry: tag or id keys, `/reload`, removals and conditions come for free, and one value names both the target and its stage.
- **Performance:** spread, catch-up and visual stage changes must be budgeted per tick and measured on foundry (phase 12 includes client FPS under heavy spread). The spread engine is measured by `SpreadBenchmark`, a gametest generator registered only when `REMISSION_SPREAD_BENCHMARK` is set (`REMISSION_SPREAD_BENCHMARK=1 ./gradlew runGameTestServer`); it writes `run/gametest/spread-benchmark-<case>.txt`.
- **Spread is chunk to chunk along one parent path:** each chunk takes the Strain from a single neighbour toward each nidus, so a cancelled spread attempt (a firebreak) holds everything behind it, and catch-up can be closed form because the steady state is `100 - distance * falloff`.
