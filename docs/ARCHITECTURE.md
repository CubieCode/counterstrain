# Architecture and decisions

## Current boundary

Phase 0 was scaffold only: deferred registers, configs, payload registrar, datagen providers and one smoke gametest. Phase 2 is complete: P2.1 adds the `corruption` entity attachment, its server API and the host stage thresholds config; P2.2 adds the host render layer and its client intensity option; P2.3 adds the `/remission` debug commands (below). Phase 3 has started: P3.1 adds host goals and attack attributes (Behaviour, below); P3.3 adds infection on kill, `#remission:immune`, the `remission:mob_profile` datapack registry, the `remission:is_corrupted` loot condition and the host tissue loot modifier. Phase 4 has started: P4.1 adds the `chunk_corruption` chunk attachment, the `remission:nidus` block and its saved index, and the budgeted spread engine with its `spread` config (festering land, below). P4.4 adds the public API package `com.cubiecode.remission.api` (events and queries, below). P4.2 adds the festering blocks, the `remission:fester` biome, the `festers_into` and `fester_variant` data maps and the stage work that turns land and flips biomes (festering land, below); P4.6 extends it to cave walls, floors and ceilings with `festered_deepslate` and an `underground_stage` per data map entry. P4.5 makes live passes skip chunks still queued for catch-up. P4.7 adds festering land infection: the `festering_exposure` entity attachment, the `[infection]` config and `CorruptionCause.FESTERING_LAND` (festering land infection, below). Phase 6 has started: P6.1 adds the scanner and scan data items; P6.2 adds the `bestiary` player attachment and the bestiary screen (research, below). Phase 7 has started: P7.1 adds the miasma fluid, the optional Mekanism miasma chemical and the sample items with their loot (tech chain, below). Phase 8 has started: P8.1 adds the `quest/` advancement triggers and the `RemissionStats` custom stats (contracts table, below). Everything below marked *planned* is a roadmap item.

## Repository and products

```text
                 ┌───────────────────────────────┐
                 │ Counterstrain (pack/)         │
                 │ KubeJS · FTB Quests · datapack│
                 │ story, recipes, balance       │
                 └──────────────┬────────────────┘
          data/scripts only     │  (tags, per-mob JSON, recipes, triggers,
          never Java imports    │   stats, commands, API events via KubeJS)
                 ┌──────────────▼────────────────┐
                 │ Remission (mod/)              │
                 │ generic defaults, no pack deps│
                 └──────────────┬────────────────┘
                                │ optional, guarded integrations
              Mekanism · AE2 · Create · Ars Nouveau · EMI/JEI · JourneyMap
              and the phase 10 mod-side tie-ins (DESIGN: Pack integrations)
```

- Remission requires only NeoForge. Integrations with other mods are optional (`compileOnly` against the mod, declared `type="optional"` in `neoforge.mods.toml`, runtime checks via `ModList`) and live in `integration/<modid>/`; Mekanism (P7.1) is the first. Remission never hard-depends on an integrated mod.
- Integrations and addons build on the public API (`com.cubiecode.remission.api`, below). Pack-side integration (KubeJS, datapacks) is preferred; mod-side code is used only where the other mod's content can be registered or hooked only from Java (DESIGN, Pack integrations).
- The pack talks to the mod only through data and script surfaces (below). If the pack needs something the mod cannot express, extend the surface generically rather than special-casing the pack.

## Naming in code

Internal Java system names and public API types may keep the generic word "corruption" (`CorruptionState`, the `corruption` attachment, `remission:is_corrupted`); content IDs, lang keys, triggers, stats and commands use the Strain glossary in [DESIGN](DESIGN.md#glossary). Do not rename either side to match the other.

## Planned systems and data flow

### Corruption state (phase 2, built in P2.1)

- `CorruptionState(level, stage)` in `corruption/`: `level` 0–100 (`MAX_LEVEL`), `stage` the number of `hosts.stageThresholds` entries the level met when it was set (default `[1, 34, 67]`, so stages 1–3; 0 means not a host). `variant` (the resistant mutation a host carries) is reserved for P9.1 and not stored yet. Field-level contract: remission-data-formats.
- Attachment `remission:corruption` (`RemissionAttachments.CORRUPTION`) on any entity; the API takes `LivingEntity`. Codec-serialized with the entity (`neoforge:attachments`), skipped at level 0, so it survives save/reload and dimension change (non-player entities are recreated with `restoreFrom`, which copies saved data; players keep their entity). Not copied on death or by vanilla living conversions; infection's own `convert_to` sets it on the replacement (below).
- Server API `Corruption.get(entity)` (never creates the attachment), `Corruption.set(entity, level)` (clamps, restages from config, removes the attachment at 0, no-op if unchanged, throws on the client), `Corruption.isHost(entity)`, `Corruption.isImmune(entity)` (`#remission:immune`; `set` ignores levels above 0 for immune entities). `set` applies or removes mob profile attribute modifiers when host status changes, then posts the API's `HostCorruptedEvent` or `HostCleansedEvent` when the state changed; `set(entity, level, cause)` names the `CorruptionCause` (infection on kill passes `INFECTION`, festering land infection `FESTERING_LAND`, the debug commands `COMMAND`, the two-argument form `OTHER`).
- Stages are computed when a level is set, never on load or on the client, because common config is not synced and may differ per side. Changing the thresholds restages a host only when its level next changes.
- **Sync decision: NeoForge attachment sync** (`AttachmentType.Builder#sync(StreamCodec)`, present in 21.1.259), not a custom payload. NeoForge's `AttachmentSync` sends `setData`/`removeData` changes to `chunkMap.getPlayersWatching(entity)` plus the entity itself when it is a player, sends the full state in the start-tracking pairing data (`ServerEntity.sendPairingData`), and resends a player's own attachments on login, respawn and dimension change. That covers every case P2.1 requires with no Remission code, removal included. Synced attachment types are a synced registry, so client and server must both have Remission (already required: `side="BOTH"`). `RemissionNetwork.PROTOCOL_VERSION` is unchanged; the wire format is `CorruptionState.STREAM_CODEC` (two var-ints), so changing it is a protocol change for the synced registry. A custom payload would only be worth it for batching or per-player filtering beyond tracking, which nothing needs yet.
- Client: `HostOverlayLayer` draws hosts from the synced state (host rendering, below).

### Host rendering (phase 2, built in P2.2, layers in P2.4)

- `HostOverlayLayer` is added in `EntityRenderersEvent.AddLayers` to every renderer that is a `LivingEntityRenderer`: each `getEntityTypes()` renderer plus every player skin renderer. No per-entity-type code, so modded mobs get it too. Renderers that are not living-entity renderers (the ender dragon's, GeckoLib-style renderers) cannot take layers and are skipped; the count is logged at startup. At render time the layer also skips a null model or texture, invisible entities and non-hosts.
- The layer re-renders the parent model after the mob's own pass, so it inherits that frame's pose, baby scaling and model-part visibility. It calls `setupAnim` again with the frame's arguments before each pass, because some models keep per-draw state and clear it after drawing (Mekanism's robit model drops its entity and would draw nothing); vanilla `setupAnim` is idempotent. Armour, wool and other own-model layers get their own companion (below); held items are not overlaid.
- Render type `remission_host_overlay` (`HostRenderTypes`, memoised per mob texture, pattern and layering state): shader `remission:host_overlay` (vanilla `rendertype_entity_translucent` vertex stage, own fragment stage), translucent blending, no culling, lightmap and hurt overlay, colour writes only. It binds the mob's texture to sampler 0 and the Strain pattern to sampler 3, and discards fragments where the mob texture is transparent, so empty outer-layer boxes (hats, jackets, the drowned's outer layer) stay invisible. The pattern repeats at one pattern texel per mob texel whatever the mob texture's size.
- Stage drives the look: `textures/entity/host/stage_1..3.png` (stages above 3, from extra thresholds, use stage 3), plus a full-bright `veins_glow.png` pass from stage 3. The client reads only the synced `stage`; it never restages. All four textures are placeholders (CONTENT-PROVENANCE).
- Client config `hosts.overlayIntensity` (0–1, default 1) is the overlay's vertex alpha; 0 turns it off. Presentation only.
- Layers with their own model or texture (P2.4): `HostLayerOverlay` adds, in `AddLayers` at `EventPriority.LOWEST` (so layers other mods add in the event are seen), one companion per `HumanoidArmorLayer`, `SheepFurLayer`, `SlimeOuterLayer`, `DrownedOuterLayer`, `HorseArmorLayer` and `WolfArmorLayer` (or subclass) in every living-entity and player skin renderer, vanilla or modded, appended with `addLayer` to the end of that renderer's layer list (after eyes, held items and the other layers), not next to the layer it wraps. For a host it runs the wrapped layer again (once per pattern, plus the glow pass from stage 3) with a buffer source that sends each `NEW_ENTITY`-format draw into `remission_host_overlay` for that draw's own texture and layering state (armour is drawn with `VIEW_OFFSET_Z_LAYERING`, nudged towards the camera, and an un-offset overlay would lose the depth test), with the overlay colour instead of the layer's dye; glint (other vertex format), the armour-trim atlas and outlines are dropped. The layer's own logic therefore picks the pieces, models and textures (NeoForge custom armour models and textures included), and the overlay follows each layer texture's cutout. Eye and emissive layers (`EyesLayer`, energy swirls) are never wrapped. Reading the renderer's `layers` list and a render type's texture uses reflection (`ObfuscationReflectionHelper`, Mojang names at runtime) rather than a mixin or access transformer. Failures degrade without crashing: if the reflective handles cannot be resolved, one error is logged and no companions are added; if a renderer's `layers` list cannot be read, one warning per such renderer and it gets none; if a render type's texture cannot be read, one warning per failing render type (the empty result is cached) and draws of that type get no overlay. Nothing else changes. Where two draws of one layer cover the same texels (leather's undyed overlay, dyed or cracked wolf armour) the pattern is applied twice there and looks slightly stronger. A wrapped layer must not hold two entity-format buffers open at once (vanilla's do not); the overlay buffers would end each other's batch.
- Limits: other layers (saddles on pigs and striders, llama decor, villager and horse markings, held items, heads, elytra, capes) are not overlaid; renderers that are not `LivingEntityRenderer`s (GeckoLib-style) get nothing. Stage particles (DESIGN) are not built yet.
- Harness scene `corruption/stages_layers` (P2.4) shows stages 0–3 on armoured zombies (iron, dyed leather), a skeleton, a fully armoured armour stand, a drowned, white and red sheep, a slime, a wolf in wolf armour and a horse in iron horse armour, plus the armoured player at stage 3 in third person.
- Harness scenes `corruption/stages_vanilla` and `corruption/stages_modded` (visual-checks) show stages 0–3 on a vanilla lineup (baby, armoured, player in third person) and on the Mekanism robit with non-standard vanilla renderers (armour stand, slimes, guardian). The wither and the ender dragon are immune bosses (`#c:bosses` in `#remission:immune`, P3.3): the scene still corrupts them, but they stay clean beside the hosts, so the `ender_dragon` shot (a renderer without the layer) and the wither now show an immune boss rendering normally.

### Research (phase 6, built in P6.1)

- `remission:scanner` makes data items: a host gives `remission:host_scan`, a block gives `remission:block_scan`, a living non-host gives nothing. The data item carries the `remission:scan_data` component (`ScanData`: host entity type id and stored host stage, or block id), registered in `RemissionDataComponents` as persistent and network-synchronized. Field contract: remission-data-formats ("Scanner and data items").
- The server decides and writes; the client only claims the interaction (arm swing). Entity scans run from `PlayerInteractEvent.EntityInteract` / `EntityInteractSpecific` so they come before the target's own interaction (villager trading, mounting); block scans run from `onItemUseFirst`, before the block's use. A 20-tick item cooldown follows every attempt and also stops a double scan when both entity events fire.
- Feedback is a vanilla action-bar message; no payloads. The scan reads host state through `Corruption.get` and never changes it.
- No timestamp or player is stored, so identical scans stack and recipe ingredients can match the full component value (NeoForge components ingredient).
- Each host scan fires `remission:host_scanned` and counts `remission:hosts_scanned`; each block scan fires `remission:block_scanned` and counts `remission:blocks_scanned` (P8.1). Later: machines that consume scans (P7.2). The scanner sits in the vanilla Tools and Utilities tab until Remission has its own creative tab.
- Harness scene `research/scanner` (visual-checks): the three items in item frames, and an armour stand pointing the scanner at a stage 2 host cow.

### Research: bestiary (built in P6.2)

- Host types are not a list: `Bestiary.isHostType` takes every registered entity type that has default attributes (every living type must register them, so this needs no entity instance), is not `minecraft:player`, and is in neither `#remission:immune` nor `#remission:bestiary_hidden` (P6.3). Installed mods widen it at once (79 types in dev runs with Mekanism: vanilla plus the robit). Players can still carry the Strain and be scanned as hosts; they are just not a bestiary entry. `#remission:bestiary_hidden` keeps infectable types that survival players cannot normally meet as hosts out of the list and total: Remission ships giant, illusioner and armour stand, and packs extend or replace it. It is a tag rather than a heuristic such as "has a spawn egg", which would drop modded mobs like the robit.
- Progress is the player attachment `remission:bestiary` (`BestiaryProgress`: entity type id → highest host stage scanned). `Scanning.scanEntity` calls `Bestiary.recordScan` on the server whenever it gives a host scan; only bestiary host types are recorded (a scanned host player, for one, is not), and a lower stage never lowers the record. Saved with the player (only when non-empty) and copied on death. Synced through NeoForge attachment sync, so no custom payload and no `PROTOCOL_VERSION` change: updates go to the owning player only (`Bestiary.syncsTo`), but NeoForge's initial sync when a client starts tracking an entity ignores that predicate, so clients tracking the player also receive the current map. That is harmless: the screen reads only the local player's progress. Field contract: remission-data-formats ("Bestiary").
- Client: `client/research/BestiaryKeys` (a `Dist.CLIENT` subscriber, not `RemissionClient`) registers the key mapping `key.remission.bestiary` (category `key.categories.remission`, default M, in game only) and opens `BestiaryScreen`, a read-only vanilla list: header "X of N host types scanned" (lang `gui.remission.bestiary.progress`), one row per host type (spawn egg icon if the type has one, name, mod name, highest stage scanned or "Not scanned"), scanned types first, then by mod (vanilla first) and name. The client computes the host types itself from its registry and the synced entity type tags. No custom GUI art.
- Harness scene `research/bestiary` (visual-checks): shot `hosts` shows the scanned hosts in the world, shot `list` opens the bestiary through the key mapping.

### Behaviour (phase 3, goals and attributes built in P3.1, fallbacks in P3.2)

- **When:** `HostBehaviours.update(mob)` brings a `Mob`'s goals in line with its host state. It runs on `EntityJoinLevelEvent` (server, low priority so other mods' goals are in first) and from `Corruption.set`, so `/remission infect`, `cleanse` and any later infection source act on loaded mobs at once. Nothing runs per tick. It is idempotent: a host that already has host goals, or a non-host without them, is left alone. `Corruption.set` calls it directly, before posting the host corrupted / cleansed events (P4.4), so listeners see a host with its goals in place.
- **State:** what was removed and added (goal, priority) lives in the transient attachment `remission:host_goals` (`AppliedHostGoals`): never saved, synced or copied. Goals are not saved either, so a mob loaded from disk rebuilds its own goals and gets host goals again on join if it is still a host; a mob cleansed before saving loads as a normal mob. Cleansing a loaded mob restores its stripped goals at their old priorities and removes the added ones in-session, and clears its target.
- **Behaviour seam:** `HostBehaviours.behaviourFor(mob)` returns the mob's `MobBehaviour` and is the only place goal application asks. Profile first: the `behaviour` of the mob's `remission:mob_profile` (`MobProfiles.find`) when it sets one, else `HostBehaviours.categoryDefault(mob)`. Overloads `behaviourFor(mob, profile)` and `update(mob, profile)` take an explicit profile (tests). Because goals are applied once per host transition and on join, a changed profile reaches loaded hosts on the world reload that loads it. Category defaults, first match wins: for brain-based mobs (any registered memory, `HostBehaviours.isBrainBased`), `melee` when the brain registers `attack_target`, the memory its fight activity acts on (piglins, piglin brutes, hoglins, zoglins, axolotls, breezes, wardens, frogs), else `none` (villagers, allays, goats, camels, sniffers...); `flying` for `FlyingMob`, `FlyingAnimal`, `AmbientCreature`, category `ambient` or flying navigation (bats, parrots, bees, ghasts, phantoms); `swimming` for `WaterAnimal`, the water categories or water-bound navigation (fish, squid, dolphins, guardians); `ranged` for `RangedAttackMob` (skeletons, snow golems, llamas, witches); `melee` for everything else (cows, sheep, pigs, zombies, spiders, slimes, modded goal-based mobs).
- **Default profile:** `remission:unsupported` (priority -1000) marks villagers, allays and frogs `none`: their brains cannot fight a chosen target (no fight activity; a frog's tongue only takes frog food). They still become hosts and render as hosts; they just keep their own AI. Contract: remission-data-formats, Mob profile.
- **What each value does** to a goal-based host:
  - `melee`: strips passive goals (breed, tempt, avoid/flee, panic, follow parent/owner/mob/boat/caravan, sit, beg, shoulder, run around, trading) and the whole target selector, then adds `HurtByTargetGoal` (priority 1, pathfinders only, no alerting), `NearestAttackableTargetGoal<Player>` (2) and `NearestAttackableTargetGoal<LivingEntity>` (3), both line-of-sight and limited to attackable non-hosts. If the mob has no attack goal (`MeleeAttackGoal`, `RangedAttackGoal`, bow or crossbow goal) it gets `MeleeAttackGoal` (priority 1, speed 1.2) when it is a `PathfinderMob`; other mobs (slimes) keep attacking through their own goals.
  - `ranged`: as `melee`, but a mob without an attack goal gets `RangedAttackGoal` (speed 1.0, 40 ticks, radius 12) when it is a `RangedAttackMob`.
  - `passive_hostile`: strips the same goals, adds only `HurtByTargetGoal` and an attack goal: it never picks fights but fights back against anything except hosts.
  - `flying`, `swimming`: strips and targets as `melee`, then adds `HostPursuitGoal` (priority 1, move and look) instead of a melee goal, whatever attack goals the mob has. It closes on the target and calls `doHurtTarget` in melee reach every 20 ticks, so damage is the `attack_damage` attribute (2 by default; profiles raise it). Movement: flying or water-bound navigation when the mob has it and a path exists (parrots, bees, fish, dolphins), else it steers the mob's velocity straight at the target at about 0.35 blocks per tick (bats, which steer themselves and have no flying navigation); vanilla squids move only along their movement vector, so a squid is steered through `Squid.setMovementVector`. A resting bat is woken whenever it settles mid-chase. A host bee stings on every hit (the pursuit goal ignores `hasStung`, so each hit poisons) and, as in vanilla, dies some time after its first sting. A `swimming` host pursues only while it and its target are both in water, so fish never beach themselves chasing land prey. Monsters (`Enemy`: ghasts, phantoms, guardians, modded flying monsters) get no pursuit goal: they fight whatever target Remission's target goals give them with their own goals (fireballs, swoops, lasers).
  - `none`: no goal changes (villagers, allays and other brain mobs that cannot fight, and an explicit opt-out for profiles).
- **Brain-based hosts** (no mixins): brain AI ignores goals, but `Mob.serverAiStep` still ticks the goal and target selectors of every mob. For a brain mob, every attacking behaviour (`melee`, `ranged`, `flying`, `swimming`) strips as above and adds `BrainHostTargetGoal` (target selector, priority 2, no flags) instead of target and attack goals. Every 10 ticks it keeps the brain's `attack_target` memory on the nearest visible prey within `follow_range` capped at 16 blocks, the range vanilla brain sensors and piglin and breeze target checks use (players first, then any attackable non-host). Fight activities drop targets their own checks reject, so on every pass, including while the current target stays valid, it also feeds what those checks read: `angry_at` for 600 ticks where the brain registers it (piglins and piglin brutes keep only a target they are angry at or chose), and for a warden, anger at the target up to `angry` plus a 1200-tick dig cooldown (a warden fights only while angry at its target, and one that did not emerge has no dig cooldown, so it would dig away instead). The brain's own fight activity then moves and attacks (piglin melee or crossbow, hoglin tusks, axolotl bites, warden roar, melee and sonic boom, breeze wind charges), so reach and damage are the mob's own. A breeze still attacks only players and iron golems (`Breeze.canAttackType`). A brain without `attack_target` keeps its own AI even if a profile asks for an attacking behaviour. `passive_hostile` changes nothing on a brain mob, which already retaliates through its brain. Cleansing removes the goal and erases `attack_target` and `angry_at`.
- **Hosts never target hosts:** a `LivingChangeTargetEvent` listener clears any target a host would set on another host, for every host whatever its behaviour (brain `StartAttacking` included). Target goals re-set their target each tick they continue, so a target that becomes a host mid-fight is dropped on the next tick.
- **Attributes:** `EntityAttributeModificationEvent` adds `attack_damage` (default 2) and `follow_range` (default 32) to every entity type with attributes that lacks them, so attack and target goals work on any mob. Profile attribute modifiers (`HostAttributes`, P3.3) are applied in `Corruption.set` before host goals.
- **Tests:** `HostFallbackTests` (own batch `host_fallbacks`, `remission:host_arena`, flooded for swimmers): host bat and parrot hurt a pig; ghasts and phantoms get target goals but no pursuit goal; host cod, squid and dolphin hurt a salmon in water; a host cod on land ignores an adjacent pig; host piglin, hoglin and warden hurt a pig, a host axolotl hurts a dolphin and a host breeze hurts an iron golem; villagers, allays and frogs resolve to the default profile's `none` and get no host goals; a pack's priority 0 frog profile without `behaviour` replaces the default and the frog falls back to `melee`; cleansing a piglin removes its brain goal and attack target. `HostBehaviourTests` (own batch, `remission:host_arena`): host cow, zombie and Mekanism robit (dev runtime only; skipped without Mekanism) hurt an uninfected pig; a host sheep hurts a survival player; hosts ignore hosts (including retaliation and a forced `setTarget`); a target that becomes a host is dropped; cleanse restores goals in-session; reload re-applies host goals on join and a cleansed save loads normal; category defaults; every living type has the attributes.
- **Harness scene** `behaviour/fallbacks` (shots `brain`, `flying`, `swimming`): stage 2 hosts of each category (brain mobs on a floor and flyers, a ghast standing in for flying monsters, in the air, each beside an uninfected pig; swimmers on a dry floor, because animated water textures and the phantom's id-offset wing flap are not pinned by the frozen tick and made shots differ between runs), so the overlay is checked on every fallback category. Ticks are frozen in harness scenes, so pursuit itself is covered by the gametests. Infection: below (P3.3).

### Infection, mob profiles and host loot (phase 3, built in P3.3)

- `Infection` listens to `LivingDeathEvent` at `LOW` priority. A dying `Mob` whose damage source's responsible entity is a host is not killed: the event is cancelled and it becomes a host at the lowest stage threshold, in place (healed, same entity, no death loot) or, with a profile `convert_to`, replaced through `Mob.convertTo` with NeoForge's `LivingConversionEvent` pre/post. In-place keeps the entity's data (trades, owner, inventory); the replacement joins the level before it is infected, and `Corruption.set` then applies its attributes and host goals.
- `#remission:immune` (default `#c:bosses` only; players stay infectable for the overlay, scanning and commands, and infection on kill never takes them because it only converts `Mob`s) is enforced in `Corruption.set`, so every route (infection, conversion, commands, future sources) respects it.
- Festering land infection (P4.7, below) goes through the same conversion path with `CorruptionCause.FESTERING_LAND`; `Infection.canInfectFromFesteringLand(Mob)` checks its eligibility (immune, host, profile flag).
- `remission:mob_profile` is a server-only datapack registry (`DataPackRegistryEvent.NewRegistry`, no network codec). **Reload decision:** datapack registries are read when a world loads and are frozen afterwards, so profile changes need a world reload; `/reload` only rebinds the tags profiles name. Making profiles `/reload`-able would mean a `SimpleJsonResourceReloadListener` with its own tag resolution; the registry was kept because HolderSet entity matching, error reporting and KubeJS/datapack tooling come for free, and profiles are tuning data rather than something changed mid-session. `MobProfiles.find` sorts by id and picks the highest priority on every call (no cache; it runs on infection and host transitions, not per tick).
- `HostAttributes` applies a profile's `attributes` as permanent `add_value` modifiers (`remission:mob_profile`), so they save with the entity and a host's health above its base maximum survives reload; it removes them on cleanse and reconciles them when a host joins a level.
- Loot: `remission:is_corrupted` reads the stored stage of a loot context entity. The default global loot modifier `remission:host_samples` (codec `remission:add_item`) adds one `remission:host_tissue` to a host's death loot; `minecraft:damage_source_properties` with no predicate keeps it to death drops.
- Gametests: `InfectionTests`, `MobProfileTests` (including a profile `behaviour` overriding the category default in applied goals), `HostLootTests`. The phase exit scene `behaviour/conversion` was outside P3.3's assigned scope and is still open.

### Festering land (phase 4; levels, nidi and spread built in P4.1)

- Chunk attachment `remission:chunk_corruption` (`RemissionAttachments.CHUNK_CORRUPTION`): `ChunkCorruption(level, last_update_game_time)`, level 0–100, saved with the chunk (never at level 0), server only (no sync: clients see stages through the festering blocks and the flipped biome, P4.2, which reach them as ordinary block and biome updates). Levels only rise in phase 4. Field-level contract and config: remission-data-formats.
- Nidi: block `remission:nidus` (`NidusBlock`, block entity `NidusBlockEntity`, drops a nidus core since P7.1, pistons cannot move it). `NidusIndex` is a `SavedData` per level (`data/remission_nidi.dat` in the dimension folder) mapping each nidus position to the game time it was indexed. `onPlace` and the block entity's `onLoad` (covers nidi placed by worldgen or structures) add it; `onRemove` removes it, and a pass that finds a loaded index entry without its block drops it. Breaking a nidus stops its spread at once; its land keeps its level.
- Spread engine (`SpreadEngine`, one per server level, run from `LevelTickEvent.Post` by `FesteringLand`): a pass starts at each multiple of `spread.intervalTicks` of level game time and visits, nidus by nidus in index order, every chunk within the nidus's Manhattan radius, nearest first. The nidus chunk gains `nidusGrowth` per pass up to 100. Another loaded chunk at distance `d` gains `spreadStep` up to `100 - d * falloff` from its parent, the neighbour one step closer to the nidus along the larger offset axis, once the parent has reached `spreadThreshold` (an unloaded parent counts as at its own target). The radius follows from those numbers (7 chunks by default). A pass stops after `chunkBudget` chunk visits and resumes next tick. Nothing depends on iteration order of hash maps or on wall time, so the same state and the same ticks give the same levels (gametest `spreadIsDeterministic`). Overlapping nidi each add their step.
- Catch-up: `ChunkEvent.Load` only queues the chunk (the chunk is not yet in the level then); each tick up to `catchUpBudget` queued chunks are fast-forwarded in closed form: for each nidus in reach, the passes missed since `max(last_update_game_time, nidus indexed)` times the rate, capped at the target. Like a live pass, it holds a step whose parent is loaded and below `spreadThreshold` (an unloaded parent counts as at its target), so a firebreak holds after a reload while the firebreak chunk is loaded; a chunk whose loaded, below-threshold parent is itself still queued catches that parent up first (recursively, at most `radius` deep, stopping at cycles between nidi; the parent's own queue entry is then skipped), so a region that loads at once catches up from the nidus outward in any load order (gametests `catchUpRespectsFirebreak`, `catchUpOrderDoesNotMatter`). A live pass skips a chunk still queued for catch-up (P4.5), so a pass that comes due before a backlog drains cannot step it and move `last_update_game_time` to now; the catch-up then credits every pass it missed, the skipped one included (gametest `livePassWaitsForCatchUp`). That converges on the same targets as live spread, so land keeps festering while nobody is near, and a reload costs the same however long it was away. Unloaded chunks are never loaded by the engine.
- Hooks: `SpreadHooks` posts the public land events (P4.4): `spreadAttempt` posts `StrainSpreadAttemptEvent` before each chunk-to-chunk step, live and catch-up, and returns the amount scaled by its multiplier (fraction resolved by a hash of the step and game time, so spread stays deterministic), 0 if cancelled; `chunkLevelChanged` posts `ChunkStageChangedEvent` after a change that moves the chunk's festering stage (`[festering] stageThresholds`; one per chunk for a catch-up); `nidusDestroyed` posts `NidusDestroyedEvent` after removal from the index. No player is passed for a destroyed nidus.
- Festering stage: a chunk's stage is the number of `festering.stageThresholds` (default `[1, 25, 50, 75]`) its level meets, computed on the server from the current config whenever it is needed, never stored. P4.2 applies it to the land (below).
- Measured cost (foundry, `SpreadBenchmark`, below): default config with 16 nidi over 1,024 loaded chunks adds 0.9 µs per tick on average and at most 0.13 ms in a tick (about 0.34 ms per 400-tick pass); a stress case of 64 nidi with a pass every second spends the full 256-visit budget every tick at 27 µs mean and 0.09 ms max. Catching up 1,024 chunks took 32 ticks at most 0.18 ms (16 nidi) or 0.29 ms (64 nidi) each in P4.1; with P4.4's parent-first rule it is still 32 ticks, at up to about 0.3 ms (16 nidi) or 0.9 ms (64 nidi) each (Public API, below).

### Festering stages and biome flip (phase 4, built in P4.2)

- `FesteringStages` turns a chunk's stage into land. A stage rise (`ChunkStageChangedEvent` from the spread engine, live or catch-up) or a chunk load queues the chunk per level; each `LevelTickEvent.Post` does up to `COLUMN_BUDGET` (64) units, one per column festered or queued chunk skipped, so a chunk takes 4 ticks, then queues it for the cave pass (P4.6, below). Work reads the chunk's stage when it starts. A chunk that leaves full status mid-way (or is queued while not at full status) is parked and queued again when it is back at full status or, if it unloads, by its load event.
- Per column, from the `WORLD_SURFACE` height down through trees, plants and water to `GROUND_DEPTH` (5) blocks into the ground (first block that blocks motion and is not a log or leaves), each block whose `remission:festers_into` data map entry has `stage` ≤ the chunk stage is replaced, keeping shared state properties, with flags `UPDATE_CLIENTS | UPDATE_KNOWN_SHAPE` (no neighbour updates, so no decay or drop cascades; light is updated by `setBlock` as usual). Block entities are skipped. `BlockFesteredEvent` is posted per replaced block.
- At the last stage (`CorruptionQueries.maxChunkStage()`), after the blocks, `flipBiomes` rewrites every biome cell of the chunk through `ChunkAccess.fillBiomesFromNoise` with a resolver that maps each cell's current biome to its fester biome (`fester_variant` entry, else `remission:fester`; `remission:fester` and every variant target map to themselves), marks the chunk unsaved and calls `ChunkMap.resendBiomesForChunks`, the vanilla `/fillbiome` path: players who have the chunk get `ClientboundChunksBiomesPacket`, and the client replaces the biomes, clears the tint caches of the chunk and its neighbours and rebuilds their sections. A player still waiting for the chunk gets the new biomes with it. No Remission payload; `PROTOCOL_VERSION` is unchanged.
- Chunk attachment `remission:festered_stage` (int, saved, server only) records the stage a chunk was brought up to, written only when the cave pass finishes, so queued chunks already there cost one attachment read, and an interrupted chunk is redone (both passes are idempotent) on its next load. Nothing reverts; purification (P5.2) will need to lower or clear it.
- Blocks: `festering_grass` (`SnowyDirtBlock`: no spreading or decay, in `#minecraft:dirt`, so it also yields festered soil, P7.1), `festering_log` (`RotatedPillarBlock`, in `#minecraft:logs` so leaves around it keep their distance), `festering_leaves` (`LeavesBlock`, in `#minecraft:leaves`, `cutout_mipped`), `festered_stone`, and since P4.6 `festered_deepslate` (`RotatedPillarBlock` with deepslate's properties). Models and textures are untinted; their colour is in the placeholder textures (CONTENT-PROVENANCE).
- Data: `festers_into` (blocks, default grass 1, logs and leaves 2, `#minecraft:stone_ore_replaceables` to festered stone and `#minecraft:deepslate_ore_replaceables` to festered deepslate 3; each entry also has an `underground_stage`, P4.6) and `fester_variant` (biomes, empty by default) are NeoForge data maps registered in `FesterMaps` (`RegisterDataMapTypesEvent`), server side, `/reload`-able. The `remission:fester` biome is datagen (`RemissionBiomeProvider`): no features or carvers, since land flips after generation. Contracts: remission-data-formats ("Festering stages, blocks and the fester biome").
- Gametests: `FesteringStageTests` (own batch): one column at stages 0–3 (cumulative, axis and persistence kept, one event per block, a repeated pass changes nothing); a queued chunk and stage events festered by the ticking work, the biome flipped at every height at the last stage, a re-queued chunk skipped; `fester_variant` resolution, the decoded value shapes, the shipped defaults and a flip into a variant. Whole-chunk tests use a force-loaded chunk 96 chunks east of the test grid and restore its biome.
- Cost (foundry, shared with other lanes, load about 6.5; a throwaway gametest over 40 force-loaded chunks, each a dense forest of 16 trees with 5x3x5 canopies over a stone layer): a whole chunk at stage 3 (every column: grass or stone, 80 logs, about 1,000 leaves) takes 0.49 ms mean, 0.33 ms median, 1.7 ms max, so a tick's 64 columns cost about 0.12 ms; rescanning a chunk with nothing left to change 0.10 ms; the last stage with its biome flip and resend 0.18 ms. Not committed as a benchmark.
- Harness scenes (visual-checks): `world/stages` (one chunk per stage 0–4, levels 0, 10, 30, 60, 90, each with a small tree, a horizontal log and a stone outcrop, set with the harness command `harness fester`; shots `overview`, `stage_0`..`stage_4`; the first shot runs `harness resend` so chunks edited while still being sent get their settled light) and `world/biome_flip` (shots `before`, `after`: a chunk flips while the client has it loaded, through the harness command `harness fester`; `inside`: the fester sky and fog from inside the flipped chunk).

### Cave festering (phase 4, built in P4.6)

- The cave pass in `FesteringStages` runs after a chunk's surface pass on its own budget: `LAYER_BUDGET` (8) block layers (16 by 16 blocks at one height) per `LevelTickEvent.Post` and level, so a full overworld chunk with stone in every section takes about 48 ticks, and a flat or empty one a few. It walks the chunk section by section, bottom to top; a section whose block palette (`PalettedContainer.maybeHas`) holds no block with an entry that festers underground at this stage (and is not already its target) costs one unit and is skipped, so air, ocean and already festered sections cost almost nothing. The stage is the one the surface pass reached, carried with the queued chunk.
- A block festers underground when its `festers_into` entry's `underground_stage` (default `FesterMaps.UNDERGROUND_STAGE`, 3; 0 is off) and `stage` are both at or below the chunk stage, and at least one of its six sides is air (`isAir`: air, cave air, void air). A side in a chunk that is not loaded counts as solid, so nothing loads chunks. Rock without air beside it and blocks without an entry (ores, dirt, gravel, sculk) are left alone; block entities are skipped as on the surface. At or above `FULL_DEPTH_Y` (0) every such block festers; below it one in `SPARSE` (4), picked by `festersBelowFullDepth`: a fastutil `HashCommon.mix` of the block position, so the result depends only on the position, not on world seed, scan order or reloads. Both are constants, not config.
- Replacement and events are the surface pass's: shared state properties kept (deepslate `axis`), flags `UPDATE_CLIENTS | UPDATE_KNOWN_SHAPE`, one `BlockFesteredEvent` per replaced block. Full opaque blocks replace full opaque blocks, so no light changes. The biome flip is unchanged (the surface pass does it at the last stage; it already covers every height).
- Resume: `festered_stage` is written when the cave pass finishes, so a chunk unloaded or parked mid-way is redone from its surface pass when it is back. No new attachment.
- Defaults: P4.2's single `#minecraft:base_stone_overworld` entry became `#minecraft:stone_ore_replaceables` (stone, granite, diorite, andesite) to `festered_stone` and `#minecraft:deepslate_ore_replaceables` (deepslate, tuff) to the new `festered_deepslate`, both stage 3. Tuff now festers into festered deepslate (it matches its colour), and a modded stone that is only in `base_stone_overworld` no longer festers by default; packs add it. Two disjoint tags because a data map file cannot override one block of a tag entry (its values are an unordered map).
- Gametests: `CaveFesteringTests` (batch `cave_festering`, plus `cave_festering_resume` alone): a hollow stone cube with ore, deepslate and tuff in its walls (exposed blocks fester with one event each, the inside and the ore stay, deepslate keeps its axis, a repeated pass changes nothing); the underground stage gate (shipped entries from stage 3, decoded `underground_stage` 1 and 0, never below the entry's `stage`); every vanilla stone's target on the surface and in a cave; a full layer at `FULL_DEPTH_Y` and a sparse one below it, matching the hash and identical when rebuilt; a chunk unloaded while its cave pass runs is not recorded and finishes every section after it loads again. Each uses its own chunk 112 or more chunks east of the test grid.
- Cost (foundry, shared, load about 3.5; a throwaway gametest, not committed, over 12 synthetic chunks of stone above deepslate up to Y=72 with about 1.7% coal ore and 40 carved cave spheres of radius 2–4 each, festered at stage 3): the cave pass takes 0.14–0.17 ms mean, 0.14–0.16 ms median, 0.42–0.44 ms p95 and under 0.5 ms max per tick at 8 layers; a rescan with nothing left to change 0.08–0.09 ms mean; the surface pass in the same chunks 0.07 ms mean. At 16 layers per tick it was 0.30 ms mean, 1.4 ms max, so the budget was halved.
- Harness scene `world/caves` (visual-checks): a carved tunnel under each of five chunks at stages 0–4 (stone with ores in the walls and tuff in the floor), one in deepslate next to sculk above Y=0 at stage 4, and one below Y=0 at stage 4 (sparse); shots `overview`, `stage_0`..`stage_4`, `deepslate_sculk`, `deep_sparse`.

Planned: surges are scheduled per level. The same engine runs in reverse for the Counterstrain (phase 9).

### Festering land infection (phase 4, built in P4.7)

- `FesteringExposure` runs one `ExposureTracker` per server level on `LevelTickEvent.Post`. Every 20 ticks a pass snapshots the level's mobs (`ServerLevel.getAllEntities()`, `Mob`s only) and checks up to 256 per tick, ending the tick early once 32 have become hosts (`ExposureSettings.INTERVAL_TICKS`, `MOB_BUDGET`, `INFECTION_BUDGET`), so a pass over more mobs, or a herd reaching the threshold together, continues on later ticks. Each checked mob in an entity-ticking chunk gains, if its chunk's Strain level (`CorruptionQueries.chunkLevel`) reaches `[infection] festeringLandMinStage` under `[festering] stageThresholds`, or loses, otherwise, the ticks since the previous pass started. Height does not matter, so caves under a festering chunk count in full; viral load (P5.1) is where height falloff belongs.
- Exposure is the entity attachment `remission:festering_exposure` (int ticks, saved with the mob, skipped at 0, server only). Immune mobs, hosts and mobs whose profile sets `conversion.festering_land` to false have it cleared; the cheap immune and host checks run before the profile lookup, and the land check before both, so mobs outside festering land cost one chunk attachment read.
- At `festeringLandExposureTicks` the exposure is cleared and `Infection.infectFromFesteringLand` turns the mob into a host at the first host stage, in place (not healed) or through its profile's `convert_to`, the same path as infection on kill, with `CorruptionCause.FESTERING_LAND` on `HostCorruptedEvent`. Turning `[infection] festeringLand` off stops the passes and freezes exposure. This is the source that creates the first hosts in normal play.
- `ExposureTracker` takes its settings, mob source and profile lookup as arguments, so tests and the benchmark drive separate trackers over chosen mobs with synthetic game times.
- Gametests: `FesteringInfectionTests` (each test alone in its own batch, in its own chunk, restoring the chunk's land and blocks afterwards; far force-loaded chunks were dropped because generating them under load could outlast the test timeout): mobs on the surface and in a sealed pocket below it become hosts after the exposure time with `FESTERING_LAND` events; immune mobs, hosts and a `conversion.festering_land: false` profile never do; nothing below the minimum stage or with the source off; exposure decays once the mob's land stops festering and survives save and load; `convert_to` replaces the mob; passes spend the check and conversion budgets per tick.
- Cost (foundry, `ExposureBenchmark`, `REMISSION_EXPOSURE_BENCHMARK=1`, shared with other lanes): 400 pigs and sheep without AI in 16 festering chunks, default config, the whole level's entities as the source. Steady exposure: each 1-second pass takes 2 ticks of 117–247 µs (11.8–24.8 µs per tick averaged, 0.24–0.50 ms per second), single ticks up to 1.6 ms once under load. A wave in which all 400 reach the threshold together runs 13 ticks at 0.64–0.73 ms mean, at most 1.2 ms, with the per-tick conversion cap of 32 (`ExposureSettings.INFECTION_BUDGET`); without the cap the same wave spent 4.5–9.2 ms in each of 2 ticks (up to 11.2 ms), since a conversion (attributes, host goals, event, sync) costs about 25–40 µs against well under 1 µs for a check.

### Public API (built in P4.4, extended by each system item)

`com.cubiecode.remission.api` is the only package other mods and KubeJS bindings may rely on; everything else is internal, including `public` classes in other packages.

- Conventions: events are NeoForge events on `NeoForge.EVENT_BUS`, posted server side on the server thread by the system that owns the state change, after the change is applied, except the cancellable spread attempt, which is posted before. Batched changes (catch-up, bounded stage batches) post one event per chunk, not per block, unless the event is block-scoped. Abstract bases `HostEvent` (a `LivingEvent`) and `FesteringLandEvent` (carries the `ServerLevel`) group them; listeners register for the concrete events.
- Built events: `HostCorruptedEvent` and `HostCleansedEvent` (from `Corruption.set`, with old and new level and stage and a `CorruptionCause`), `ChunkStageChangedEvent` and `NidusDestroyedEvent` (from `SpreadHooks`), the cancellable `StrainSpreadAttemptEvent` with a mutable rate multiplier (from `SpreadHooks`, live and catch-up steps), and `BlockFesteredEvent` (from `FesteringStages`, per replaced block; P4.2).
- Built queries (`CorruptionQueries`): `isHost`, `hostLevel` and `hostStage` for any entity (both sides), and `chunkLevel`/`levelAt`, `chunkStage`/`stageAt`, `chunkStageFor` and `maxChunkStage` for land (server only; loaded chunks only, never loads one).
- Planned: surge started / ended (P4.3), viral load changed and the viral load query (P5.1), block purified and chunk entered remission (P5.2).
- Gametests: `PublicApiTests` fires each event and asserts its payload, cancels and scales spread (live and catch-up), and checks the queries for host and non-host entities at every host stage and for every chunk stage.
- Cost (foundry, `SpreadBenchmark`, shared with other lanes, so runs vary by 2x or more): live spread with the events posted and no listeners runs the stress case (64 nidi, a pass every second) at 36–69 µs mean per tick against 32 µs with the hooks stubbed out, and the default case at 0.8–1.2 µs (0.9 before); one listener each on the spread attempt and stage events (`listeners` case) gives 34–89 µs. Catch-up of 1,024 chunks still takes 32 ticks; with the parent-first rule (fix round 1) its ticks cost 51–109 µs mean (default) and 119–537 µs mean, at most 0.92 ms (64 nidi), against 38–75 µs mean and 0.23 ms before. Single ticks up to 3.3 ms (live) appeared once and did not reproduce.
- Schemas, names and firing rules live in remission-data-formats ("Public API events and queries") and change only with the code. KubeJS bindings for them are P8.3.

### Viral load (phase 5)

Player attachment `viral_load`, synced to its own player. Gain per tick in festering chunks (scaled down by height above the ground when the altitude falloff config is on), plus drinking festering water, swimming in water in festering chunks and flying through miasma clouds (spawned by surges, P4.3); decay elsewhere; serums and gear reduce gain.

### Dispersal payload (phase 9)

The Counterstrain is deployed from a dispersal source: a position, radius and rate, ticked by whatever holds it. `remission:dispersal_payload` (a placed block) is the only holder Remission needs to finish the game (P9.2). ## Runtime and test infrastructure

- Run configs: `client` (`run/client`; also loads the dev-only scene harness), `server` (`run/server`), `gameTestServer` (`run/gametest`, exits on completion), `data` (`run/data`, writes `src/generated/resources`).
- Dev runtime mods (`localRuntime`, never published): KubeJS + Rhino + Better Advanced Tooltips, ProbeJS, Architectury, FTB Library/Teams/Quests (FTB Maven, not on Modrinth), JEI + EMI, Mekanism, AE2 + GuideME, JourneyMap. Toggle `dev_runtime_mods`. CI disables them.
- Headless client: `tools/run-client-headless.sh` (Xvfb + VirtualGL EGL on the RTX 4070).
- GPU workflow: `gpu-smoke.yml` (manual dispatch or the `gpu-smoke` PR label, self-hosted foundry runner) runs `tools/run-scenes.sh`, which runs every harness scene through the headless client and compares their screenshots with `tools/compare-screenshots.sh`, then uploads logs, screenshots and diffs.
- Scene harness (dev only): the `harness` source set (`mod/src/harness/`) is a separate client-only mod, `remission_harness`, that only the `client` run loads (`loadedMods`); the jar and the other runs never contain it, and `build` compiles it so it cannot rot. It does nothing unless `-Dremission.harness.scene=<id>` is set (`tools/run-client-headless.sh --scene <id>` sets it). Then it recreates a fixed superflat world, runs the scene JSON from `mod/src/harness/resources/harness/scenes/`, saves the named screenshots and exits. See the visual-checks skill for the scene format.

## Decisions

- **Gradle 9.8.1** wrapper instead of the MDK's 9.2.1: current at scaffold time, builds with no deprecation warnings.
- **Modrinth Maven pins by version ID** where a project reuses a version number across loaders (JEI resolved to its Fabric jar by number).
- **FTB mods from FTB Maven / CurseForge:** FTB Quests, Library and Teams are not on Modrinth. The pack adds them with `packwiz cf add`.
- **Distribution:** Remission publishes to Modrinth and CurseForge; Counterstrain is CurseForge-first, and its CurseForge zip is the release artifact (DESIGN, Distribution). A Modrinth `.mrpack` cannot download CurseForge files, and the pack already needs CurseForge-only mods. `packwiz curseforge export` lists only CurseForge-sourced mods in `manifest.json` and embeds every other jar under `overrides/mods/`. That is why pack mods are sourced from CurseForge; P10.1 re-sources the current Modrinth-sourced ones. The `.mrpack` export is for local testing only.
- **EMI + JEI together:** EMI is the recipe viewer players see; it takes over JEI's runtime UI (its built-in JEI compatibility) and shows every mod's JEI plugin recipes. JEI stays installed so mods with only JEI plugins keep working. Remission's recipe viewer integration (P7.2) is a JEI plugin first, which reaches both; a native EMI plugin is added only for EMI-specific features.
- **JourneyMap for maps:** chosen over Xaero's (closed source, no overlay API) and FTB Chunks (icon-only API: chunk colouring would work on the full-screen map but not on the zoomed or rotated minimap). JourneyMap's API (`info.journeymap:journeymap-api-neoforge:2.0.0-1.21.1` from maven.blamejared.com, `compileOnly`) has `PolygonOverlay` on the full-screen map, minimap and web map, `PolygonHelper`/`MapPolygonWithHoles` to merge chunks into outlines with remission-zone holes, and a server-side overlay API. The P8.2 festering overlay uses it as an optional integration in `integration/journeymap/`.
- **No climate mods:** Tough As Nails and Cold Sweat are out; viral load is the only exposure system.
- **Integrations pack-side first:** each tie-in in DESIGN's Pack integrations table is pack-side (KubeJS, datapacks on Remission's surfaces) unless the other mod's content can be registered or hooked only from Java; then it is a guarded `integration/<modid>/` package. P10.1 owns membership (`pack/mods/`) and the `compileOnly`/dev-runtime entries for every mod-side integration, so later phase 10 lanes do not touch build files.
- **Content provenance:** player-facing content is tracked in [CONTENT-PROVENANCE](CONTENT-PROVENANCE.md); `tools/check-provenance.sh` (CI: `docs.yml`) fails when an image, sound or model has no row, and when a texture's magenta placeholder marker disagrees with its row's status.
- **Pack datapack in `pack/kubejs/data/`:** KubeJS loads it as a datapack in every world without another mod.
- **Scene harness determinism and exit:** scenes freeze the tick (`/tick freeze`) after time and weather (players keep ticking, so the harness pins the local player's `tickCount` while shooting), stop atlas texture animations at their first frame before the first shot (they advance with client ticks; since P4.6, for sculk in `world/caves`), spawn mobs without `finalizeSpawn` (no random gear or variants), and pin the image-affecting options in memory (GUI hidden, clouds off, render distance 8, FOV 70, fancy graphics). Repeated runs give byte-identical PNGs on foundry. The harness ends the process with libc `_exit` after flushing logs, because under VirtualGL's EGL back end the NVIDIA driver segfaults in `libEGL_nvidia` during libc `exit()`: a normal quit, `System.exit` and `Runtime.halt` all end with exit code 134.
- **Biome flip uses vanilla's resend:** the flip rewrites the chunk's biome containers with `fillBiomesFromNoise` and resends them with `ChunkMap.resendBiomesForChunks` (`ClientboundChunksBiomesPacket`), as `/fillbiome` does, instead of a Remission payload or a full chunk resend, so `RemissionNetwork` stays payload-free and the client's own handler refreshes tints and sections. P4.2 checked it against a lighting difference in `world/stages` (a canopy shadow missing in some runs): sky light probes showed correct light on the server and stale light on the client for chunks the harness edited while they were still pending send, flipped or not (vanilla sends no light update for a chunk pending send). That is a harness timing effect, handled by `harness resend` (visual-checks), not a flip artefact; a full chunk resend made it worse, not better.
- **Festering transformations are data maps:** `festers_into` (blocks) and `fester_variant` (biomes) use NeoForge data maps rather than tags per target or a datapack registry: tag or id keys, `/reload`, removals and conditions come for free, and one value names both the target and its stage.
- **Performance:** spread, catch-up and visual stage changes must be budgeted per tick and measured on foundry (phase 12 includes client FPS under heavy spread). The spread engine is measured by `SpreadBenchmark`, a gametest generator registered only when `REMISSION_SPREAD_BENCHMARK` is set (`REMISSION_SPREAD_BENCHMARK=1 ./gradlew runGameTestServer`); it writes `run/gametest/spread-benchmark-<case>.txt`.
- **Spread is chunk to chunk along one parent path:** each chunk takes the Strain from a single neighbour toward each nidus, so a cancelled spread attempt (a firebreak) holds everything behind it, and catch-up can be closed form because the steady state is `100 - distance * falloff`.
