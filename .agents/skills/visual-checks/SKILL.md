# Visual checks

Visual evidence is only valid from a GPU run. The log must name the RTX 4070 (headless-client); llvmpipe output is never evidence. No live view (VNC) exists, so every review works from image files.

**Sources:**
- Harness scenes (preferred): `tools/run-client-headless.sh --scene <id>` builds the scene, saves fixed-name screenshots to `.local/runs/latest/screenshots/<shot>.png` and quits (headless-client). The current scenes are listed under **Current scenes** below.
- `framebuffer.png` from a timeout run of `tools/run-client-headless.sh`: the last frame, good for "reaches title/world, no error screen".
- In-game screenshots: F2 writes to `mod/run/client/screenshots/`. foundry has no input device, so these come only from a client run elsewhere with the same pack and scene.
- `tools/collect-screenshots.sh [game-dir] [--clear]` copies PNGs (and the last framebuffer) into `.local/screenshots/<UTC>/`; review from `.local/screenshots/latest/`.
- Motion clips: add `--record [seconds]` to `tools/run-client-headless.sh` (or `tools/run-scenes.sh`) to get `.local/runs/latest/capture.mp4` (H.264, at most 1280 px wide, 30 fps; from window creation, so a scene clip starts with the loading screen and ends with the scene). It uses the host's system `/usr/bin/ffmpeg` (`x11grab`, `libx264`; headless-client). Review a clip from extracted frames, e.g. `ffmpeg -ss 30 -i capture.mp4 -frames:v 1 frame.png`, plus `ffprobe` duration and size; clips are review evidence only, never compared or committed. Stills stay the reference evidence; record motion when the item's exit criteria involve animation or movement.

**Harness scenes** live in `mod/src/harness/resources/harness/scenes/<area>/<subject>.json` (dev-only `harness` source set, never in the jar). The harness fixes the world: it deletes and recreates the superflat save `remission_harness` (seed 1210101, no structures, spectator, mob spawning, daylight and weather cycles off) and pins image options in memory (GUI hidden, clouds off, render distance 8, FOV 70, fancy graphics, smooth lighting, brightness 0.5). Then it sets time and weather, runs `/tick freeze`, runs `setup` in order, and for each shot teleports the camera, waits until chunks around it are loaded and no section compiles are queued for 40 ticks, and saves the frame. Format:

```json
{
  "time": 6000,
  "weather": "clear",
  "setup": [
    "fill -13 -61 -2 13 -61 2 minecraft:smooth_stone",
    {"spawn": "minecraft:zombie", "pos": [-11.5, -60.0, 0.5], "yaw": 0.0, "nbt": "{NoAI:1b,Silent:1b}"},
    {"spawn": "mekanism:robit", "pos": [10.5, -60.0, 0.5], "nbt": "{NoAI:1b}", "requires_mod": "mekanism"}
  ],
  "shots": [
    {"name": "front", "camera": {"pos": [-0.5, -60.0, 9.5], "yaw": 180.0, "pitch": 4.0}}
  ]
}
```

- `args` (optional): named arguments with default values, e.g. `{"item": "remission:scanner"}`. Every `${name}` in the file is replaced by the value from `tools/run-client-headless.sh --scene-arg name=value` (repeatable), else the default, before the scene is parsed; an undeclared argument or placeholder fails the scene. Values are limited to `[a-z0-9_.:/-]`, so they stay inside JSON strings and command arguments.
- `time` (default 6000) and `weather` (`clear`, `rain`, `thunder`; default `clear`).
- `fester_fog` (default `false`, P4.11): the client's festering stage fog is off in every scene, in memory, unless the scene sets this to `true`, so scenes about other things keep their references. The fester biome's own colours and sounds are not affected.
- `setup`: a string is a server command without the slash (permission 4); `{"command": ..., "requires_mod": ...}` is its object form. `{"spawn": <entity id>, "pos", "yaw", "nbt"}` adds the entity directly: no `finalizeSpawn`, so no random equipment, babies or variants, and it works for types `/summon` refuses (the robit). `requires_mod` skips a step when that mod is absent (`-Pdev_runtime_mods=false`). Any failing step fails the scene.
- `shots`: `name` (`[a-z0-9_]+`, saved as `<name>.png`) and `camera`, the player's feet position and rotation as for `/tp x y z yaw pitch`. The flat surface is y = -60.
- Ticks stay frozen for the whole scene, so mobs, fluids and animations do not move between shots; atlas texture animations are stopped at their first frame (P4.6).
- `{"corrupt": <entity selector>, "level": 0-100}` (P2.2) sets the Strain level of every living entity the selector matches through the server API (`Corruption.set`, staged by the run's common config), players included; it fails when nothing matches. Tag spawned mobs (`Tags:["stage_2"]` in `nbt`) and select them by tag.
- `harness scan <targets>` (a harness-only command, registered only while a scene runs) records a host scan of every host among the targets in every player's bestiary, as the scanner would. Non-hosts are skipped; it fails if no target is a host.
- `harness player break <pos>`, `harness player scan_host <targets>` and `harness player scan_block <pos>` make every player break the block (`ServerPlayerGameMode.destroyBlock`) or scan with the scanner (put in the main hand, cooldown cleared; `Scanning`), the server code a real break or scan runs, so stats, advancement triggers and quest tasks fire. Ticks are frozen, so add `tick step <n>` after them when something polls on ticks (FTB Quests checks stat tasks every few ticks).
- `harness player use <pos>` (P7.2) makes every player use the block with what it holds (`ServerPlayerGameMode.useItemOn`); a machine opens its menu, for spectators too. Pair it with `"screen": true`.
- `harness fester <from> <to> <level>` (harness-only, P4.2) sets the Strain level of every chunk the box overlaps and festers each at once to its stage: blocks, and the biome flip at the last stage, as the budgeted stage work would over a few ticks (no spread events).
- `harness fester <from> <to>` (harness-only, P8.2), without a level, festers every loaded chunk the box overlaps at once to the stage it already has (`FesteringStages.festerNow`). Run it after `remission region advance`, whose stage events queue the budgeted stage work, which also runs on frozen ticks: otherwise blocks change, and the map with them, while the shot settles.
- `harness veins <from> <to>` (harness-only, P4.8) grows the festering veins of every loaded chunk the box overlaps at once, at each chunk's current stage, as the budgeted vein pass would (`FesteringVeins.growNow`). Run it after `harness fester`. Frozen ticks grow no veins on their own; a `tick step` does (the level's vein pass runs on stepped ticks).
- `harness resend <from> <to>` (harness-only, P4.2) sends every loaded chunk the box overlaps to clients again, in full. Setup runs while the client is still receiving chunks; vanilla sends no light update to a player for a chunk still pending send, so a chunk edited during setup (a `fill` of leaves) can reach the client with light from before the edit and keep it (a missing canopy shadow in some runs). Run it in the first shot's `commands`, after setup, over the area the scene edits; `world/stages` does.
- `harness surge hosts <centre> <count> <radius>` and `harness surge clouds <centre> <count>` (harness-only, P4.3) spawn surge hosts within `radius` blocks of the centre and release miasma clouds over festering chunks around it through the surge code (`SurgeHosts`, `SurgeController.releaseClouds`: festering chunks only, surface or covered spots near the centre's height, type spawn rules under cover), with a random seeded from the arguments and no spawn finalisation, so every run gets the same mobs and clouds. Each fails if nothing could be placed. Spawn hosts in a later shot's `commands`, not in `setup`: cave spawn rules read light, which settles only after setup.
- A shot's optional `commands` (list of server commands, no slash) run on the server right after the camera move, before the shot settles: use them to change chunks an earlier shot already loaded on the client, so the shot shows the change arriving as an update (P4.2's `world/biome_flip` checks the biome resend this way). Any failing command fails the scene. A shot also waits until a `tick step` (from its commands) has finished on the server and the client, so it shows where the steps end (P4.3's `world/miasma_cloud` steps its clouds this way).
- A shot's optional `recipes` names a recipe category (e.g. `"recipes": "remission:analyzing"`): once the camera is in place the harness opens it in EMI's recipe screen when EMI is loaded, else in JEI's (from the inventory screen, retrying until the viewer has loaded its recipes), and the shot waits for the screen. It fails without EMI or JEI. `"screen": true` says a shot command opens a screen (such as `harness player use`), so the shot waits for it.
- A shot's optional `tooltip` (P5.7) names an inventory menu slot (9–35 main inventory, 36–44 hotbar; e.g. `"tooltip": 36` for the first hotbar slot): once the camera is in place the harness opens the survival inventory and draws that slot's highlight and item tooltip as if the mouse hovered it (the real cursor stays at the screen centre, so the slot under it is highlighted too). The scene must make the player survival or adventure (the creative inventory replaces the screen) and fill the slot; the shot fails on an empty slot.
- A shot's optional `button` (P5.8) names the lang key of a button on the screen the shot's `press` opened (e.g. `"button": "gui.remission.bestiary.tab.hazards"`); the harness presses it once the screen is open, and the shot settles afterwards. The scene fails if the screen has no such button.
- `harness notice <hazard> <pos> <count>` (harness-only, P5.8) reports `count` strikes of `hazard` at `pos` through the hazard notice API with each player as the placer, then sends every open group at once instead of after the grouping time, so the notices reach the client during setup.
- A shot's optional `map: true` (P8.2) opens JourneyMap's full-screen map once the camera is in place (JourneyMap's own key, J, is shared with other mappings, so `press` cannot), and the shot waits for it. Before opening, the harness marks JourneyMap's first-run splash as seen and sets the full-screen zoom to 2048 (four times the default), in memory only. It fails without JourneyMap. The map is centred on the camera.
- A shot's optional `press` names a key mapping (e.g. `"press": "key.remission.bestiary"`). Once the camera is in place the harness clicks that mapping's key, and the shot waits for a screen to be open instead of for none; the screen is closed before the next shot. The scene fails if another mapping active in game shares the key, since the click would reach both. The GUI is hidden only for the HUD: a screen renders, and JourneyMap may draw its minimap behind it.
- A shot's optional `hud: true` shows the GUI for that shot (hidden otherwise) and `gui_scale` sets the GUI scale (0, the default, is auto: 4 at 1920x1080); the scene must make the player survival or adventure to show health, hunger and Remission's rows. For HUD shots the harness clears chat, leaves out the camera overlays (the vignette eases per rendered frame, so it varied between runs) and turns JourneyMap's minimap off (it maps in the background). The harness pins the minimap for every shot, off for HUD shots and on otherwise (screens show it behind them, as the references do), and after a HUD shot turns it back on and saves that, because JourneyMap may save its properties mid-shot and the run directory persists: a scene never depends on the minimap setting an earlier scene left in `mod/run/client/journeymap/` (P4.10 found `world/nidus_fight` saving it off, which removed the minimap from later `tech/machines` and `tech/recipe_viewer` runs). Add `gamerule sendCommandFeedback false` to setup so command feedback does not reach chat (P5.1).
- `harness purify` (harness-only, P5.2) runs the level's quarantine pylon passes until no loaded warded chunk is festering and then every queued chunk cleanse, at once, as the budgeted passes would over minutes (frozen ticks purify nothing on their own). Place the pylon with `setblock` first, and follow it with `harness resend` over the area.
- `harness regrow` (harness-only, P5.5) regrows every column of every loaded chunk in remission at once, as the budgeted regrowth would over `regrowthTicks`; the plants depend only on position and the world seed, so runs match. Run it after `harness purify`, and follow it with `harness resend`.
- `harness reclaim <pos> <operations>` (harness-only, P7.4) runs up to that many operations of the reclaimer at `pos` at once with the configured settings, stopping at the first that drains nothing, topping its energy up before each as a generator would (fuel is used as usual), then runs every queued chunk cleanse. Give it fuel with `data merge block` first and follow it with `harness resend` over its reach.
- `harness viral_load <targets> <load> [rising|falling]` (harness-only, P5.1) sets players' viral load and the trend their meter shows through the server code. Viral load does not update while ticks are frozen, so the value holds for every shot.
- `harness nidus <pos> <vitality>` (harness-only, P4.10) strikes the nidus at `pos` down to `vitality` percent (1–100) through the fight code as the nearest player, so each threshold it passes starts its surge (and lashes survival players, so keep the scene's player creative). Ticks are frozen, so the nidus neither regenerates nor updates its boss bar between shots; the command sets both. A surge's action bar line fades on client ticks, so follow the command with `title @a actionbar ""`.
- A shot's optional `view` sets the camera type: `first_person` (default), `third_person_back` or `third_person_front`, e.g. to see the player. The scene's player is a spectator unless setup changes it (`gamemode creative @a`; a spectator renders only its head); a non-spectator falls, so its camera positions must stand on the ground (y = -60).
- `corruption/stages_vanilla` (shots `stage_0`..`stage_3`, `stage_3_oblique`, `player`) and `corruption/stages_modded` (same stage shots plus `ender_dragon`) are the host overlay scenes (P2.2). In `stages_modded` the wither and ender dragon are immune bosses (P3.3) and stay clean at every stage; references from P3.3 on show them without the overlay. Both scenes use one lineup per stage, 30 blocks apart on z, levels 0, 20, 50, 90. `corruption/stages_layers` (P2.4; same stage shots and spacing plus `stage_3_oblique` and `player`, the player in iron, diamond and gold armour at stage 3) checks that the overlay follows each layer's own cutout (no enchanted items: glint moves with wall-clock time and would break byte-identical runs). Players keep ticking under `/tick freeze`, so while shooting the harness pins the local player's `tickCount` to 0; its idle animation (arm bob) is then the same every run.

- Superflat world, fixed seed.
- `/time set 6000`, `/weather clear`, `/gamerule doDaylightCycle false`, `doMobSpawning false`.
- GUI hidden (F1-equivalent option) unless reviewing HUD.
- Fixed camera position and rotation via `/tp @s x y z yaw pitch`.
- Mobs spawned with `NoAI:1` for static lineups.

**What to look for:**
- **Hosts:** the Strain overlay follows the mob's own model, including animated parts, baby mobs, armour and held items. Stages are distinguishable at a glance. No z-fighting, black/magenta missing-texture checkerboards, or missing layers on modded models. Compare with an uninfected lineup in the same scene.
- **Festering land:** stage textures tile without seams. Biome colour flips cleanly at chunk borders. No lighting holes. Particles are on screen but don't flood it.
- **Effects and UI:** HUD and viral load meter legible at 1920x1080 and at GUI scale 2/3. Text fits. Colours hold up in the dark.

- **Provenance markers:** placeholder textures show the 2×2 magenta corner marker and placeholder GUI/promo art the "PLACEHOLDER" label; art whose CONTENT-PROVENANCE row is `final` shows neither. A mismatch is a bug (content-provenance skill).

Always compare against the accepted reference for the same scene (below), and against vanilla for "does it still look like Minecraft".

**References and comparison:** reviewed reference images are committed in `tools/visual-references/<scene>/<shot>.png`, one directory per harness scene, so local runs and the GPU workflow compare against the same set. Keep the set small: only scenes named in exit criteria or item acceptance (now `smoke/mob_lineup`, `corruption/stages_vanilla`, `corruption/stages_modded`, `corruption/stages_layers`, `research/scanner`, `research/bestiary`, `research/countermeasure_protocol`, `research/hazards_tab`, `behaviour/fallbacks`, `tech/miasma`, `tech/machines`, `tech/recipe_viewer`, `tech/serums`, `world/stages`, `world/biome_flip`, `world/caves`, `world/surge`, `world/miasma_cloud`, `world/veins`, `survival/hud`, `purification/pylon_radius`, `purification/regrowth`, `purification/reclaimer`, `survival/revenant`, `quest/map_overlay`, `world/atmosphere`, `world/nidus_fight` and `world/nidus_stages`, about 64 MB together), the harness's 1920x1080 PNGs unchanged (no re-encoding, so unchanged runs hit the byte-identical fast path), and replace files instead of adding variants. They are screenshots of the running game used as test fixtures, never shipped, and sit outside the provenance check's scan roots, so they take no CONTENT-PROVENANCE rows. Compare a run with:

```sh
tools/compare-screenshots.sh --scene <id> --actual .local/runs/latest/screenshots --out .local/compare/<id>
```

It writes `<shot>-diff.png` (the actual image dimmed to grey, pixels over the threshold red, smaller differences yellow) and `compare-result.txt` (per shot: status, differing pixels, sub-threshold pixels, largest channel delta, ratio). A pixel differs when any RGBA channel moves by more than `--threshold` (default 24 of 255); a shot passes when at most `--max-diff-ratio` of its pixels differ (default 0.0005, about 1000 pixels at 1920x1080). Exit 0 = all shots within tolerance, 1 = a shot differs, is missing, has no reference or changed size, 2 = usage or tool error, 3 = no reference for the scene. `tools/compare-screenshots.sh` wraps `tools/compare-screenshots.py` (standard library Python, PNGs decoded with zlib): about 2 s for two identical 1920x1080 shots and longer for real differences. `--self-test` runs synthetic cases. On foundry, repeated runs of a frozen scene are byte-identical, so any difference is real; the tolerance absorbs driver or minor rendering noise.

**Updating references:** only for an intentional, reviewed change. Run the scene from a GPU-verified run, look at every shot and its diff image, then rerun the comparison with `--accept` (copies the actual shots over the references and drops shots the scene no longer takes) and commit the new PNGs in the same PR as the change that caused them, with the reason in the PR body. A new scene's first reference is made the same way (exit 3, then `--accept`). Never accept to make a failing check pass without looking.

**Recording:** list in the PR each scene, the image paths or artifact name, the renderer line, the comparison result and what you checked. Attach or upload images; don't commit run output (only reviewed references, as above). Say plainly when a check could not be done.

**Acceptance:** A visual exit criterion is met only when:
- the listed scenes run in the GPU workflow (`gpu-smoke.yml` runs every scene file; dispatch it on your branch or label the PR `gpu-smoke` (headless-client has the command), and link the run),
- diffs are within tolerance or intentional changes have been reviewed and the references updated,
- an agent or human has looked at the images.

An image diff alone never accepts new visuals.
