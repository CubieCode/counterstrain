# One roadmap item

Read AGENTS.md, the item in ROADMAP.md (scope, acceptance, phase exit criteria), docs/DESIGN.md and docs/ARCHITECTURE.md. Scaffold, docs or "look into" requests do not authorise implementation. Confirm every `Depends on` item is `done` on current main and the item has no owner or open PR (`gh pr list --search "<ID>"`); otherwise report and stop. If already in an assigned worktree, use it; do not launch another worker.

Resolve the Orca executable: `ORCA_CLI_COMMAND` if set; otherwise `orca-dev` when `ORCA_DEV_REPO_ROOT` is set; otherwise `orca-ide` on unmanaged Linux such as foundry; otherwise `orca`. Never use the Linux screen reader binary. Load `<orca> skills get orca-cli` before operating it and follow the live guide's syntax. For a new independent lane use its worktree create flow with `--no-parent` and the repo default base; never base on another feature branch unless assigned stacked work. Setup runs `tools/worktree-setup.sh` (`orca.yaml`): per-lane `mod/run/` and `.local/`, a lane-specific `runServer` port, packwiz, `./gradlew build` and `tools/pack.sh check`. If setup was skipped, run `tools/worktree-setup.sh <root> <worktree>` yourself. Never copy another lane's run directories, worlds, instances or credentials.

Claim: branch `feat/<id-lower>-<slug>` (e.g. `feat/p2.1-corruption-attachment`; rename Orca's branch if needed). First commit sets your item's Status `in-progress` and Owner to the branch. Change only your item's fields, then run `python3 -I tools/roadmap-board.py` to refresh ROADMAP's status board (check-docs fails if it is stale; after a rebase, rerun it rather than hand-merging the board). Follow the item's Skills plus any specialised skill the change touches (neoforge-mod-dev for Java, remission-data-formats for contracts, packwiz-pack/kubejs-scripting for pack work, visual-checks for anything rendered).

Scope: do exactly the Scope line. Shared surfaces are serialization gates (roadmap-orchestrate): `mod/gradle.properties`/`build.gradle`, `RemissionRegistries` and registry holders, `RemissionNetwork` (`PROTOCOL_VERSION`), config specs, `RemissionDataGenerators`, `en_us.json`, remission-data-formats contracts, `pack/pack.toml` and `pack/mods/`. Touch them only as your brief allows, keep registry and lang edits append-only, and agree contracts before dependent code. Report unresolved design decisions (schema shape, sync mechanism, balance defaults) to the coordinator or user and continue independent work. Propose follow-up items in a separate `Roadmap: ...` PR rather than widening yours.

Evidence: in `mod/`, `./gradlew build runData runGameTestServer` with no `src/generated` drift; `tools/pack.sh check` if `pack/` changed; `git diff --check`; ledger rows and placeholder markers for any player-facing content (content-provenance); then the docs-sync skill (both passes) so README, ARCHITECTURE, contracts, skills, changelogs and your ROADMAP item describe what you built. Visual exit criteria need the named harness scenes (or, before P1.1, a documented manual scene) from a GPU-verified run. `tools/run-client-headless.sh` waits on the shared GPU lock, so other lanes may delay you; never bypass it. Collect and review screenshots (visual-checks). Record measured numbers when the item asks.

After rebasing on main: rerun `./gradlew runData` and `tools/pack.sh refresh` instead of hand-merging generated files (`mod/src/generated/`, `pack/index.toml`), then rerun the checks. Stacked work: after the base PR is squash-merged, `git rebase --onto main <old-base-branch>` so only your commits remain, then retarget the PR to `main`.

Close: set Status `review`, run `tools/roadmap-board.py`, commit `<ID>: <result>`, push, `gh pr create --title "<ID>: <title>" --body-file <tmp>` with scope, checks, evidence (attached images or `.local/` paths, renderer line), open decisions. Record the PR URL in your item with a follow-up commit if needed. Do not mark done before merge; do not merge unless assigned that authority. After an authorised merge the coordinator marks it done through a status PR (roadmap-orchestrate). Never remove your own worktree: after the merge, whoever merged runs `tools/cleanup-worktrees.sh` from the main checkout, which removes merged, clean lanes (run directories and `.local/` go with them, so keep evidence in the PR).

For supervised dispatch, follow the injected Orca worker contract for asks, heartbeats and worker_done; load `<orca> skills get orchestration` and its worker-contract reference if unclear. Report the PR and modified files exactly once on completion. For a direct assignment, return the PR URL and any held gate. Do not expand into the next item.
