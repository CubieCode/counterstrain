# KubeJS scripting

The pack uses KubeJS 2101.7 (Rhino 2101.2) on 1.21.1. Its API differs from KubeJS 6 (1.20.1) and older: `onEvent(...)`, NBT-based item matching, `ItemEvents.tooltip`, Architectury-era classes and many wiki/forum snippets are wrong here. The kubejs.com wiki is partly stale too. Source of truth, in order: ProbeJS declarations for this pack, the KubeJS jar (`~/.gradle/caches/modules-2/files-2.1/maven.modrinth/kubejs/`), then current docs. When in doubt, run it and read `logs/kubejs/*.log`.

ProbeJS: in a dev client (`tools/run-client-headless.sh`, or a playtest instance) with ProbeJS enabled, enter a world and run `/probejs dump`; it writes TypeScript declarations under the game directory's `.probe/` / `kubejs/probe/` (gitignored). Open the game directory's `kubejs/` in VS Code for completion. Regenerate after adding mods. Never commit generated declarations.

Locations, in `pack/kubejs/`:
- `startup_scripts/`: `StartupEvents.registry('item'|'block'|'fluid', e => e.create(...))`, `StartupEvents.modifyCreativeTab`. Runs once at launch, before registries freeze, and needs a restart.
- `server_scripts/`: `ServerEvents.recipes`, `ServerEvents.tags('item'|'block'|'entity_type', ...)`, `ServerEvents.recipeSchemaRegistry` and gating logic. Reload with `/reload`.
- `client_scripts/`: `ItemEvents.modifyTooltips`, `RecipeViewerEvents.*` (one API for both viewers; server-driven in 2101; EMI support is partial: adding/removing entries and hiding recipes, so check results in EMI, which is what players see), `ClientEvents.lang`. Applied on resource reload (F3+T) or restart.
- `data/` and `assets/`: datapack and resource pack loaded automatically (the pack datapack, e.g. `kubejs/data/remission/tags/entity_type/immune.json`).

Name files by topic (`server_scripts/recipes/mekanism.js`, `server_scripts/gating/chapter1.js`); scripts load alphabetically. Start each file with a header comment saying what it changes and why.

Recipes: `event.shaped(Item.of('x', n), [rows], {A: 'id'})`, `event.shapeless`, `event.smelting`, `event.remove({output: 'id'})` / `{id: 'mod:recipe'}` / `{mod: 'x', type: 'y'}`, `event.replaceInput(filter, from, to)`; give added recipes stable ids with `.id('counterstrain:...')`. Mod recipe types: use the typed methods ProbeJS shows (`event.recipes.mekanism...`, `event.recipes.create...`); fall back to `event.custom({type: ..., ...})` with the mod's 1.21.1 JSON.

Remission recipe types (`remission:analyzing`, `sequencing`, `synthesizing`) get KubeJS methods from JSON schemas the mod ships in `data/remission/kubejs/recipe_schema/` (P7.3; keys and constructors in remission-data-formats, "Synthesizer products and KubeJS recipe schemas"). Results come first: `event.recipes.remission.synthesizing(['2x remission:serum'], ['remission:strain_sequence', '2x minecraft:glass_bottle']).fluidIngredient(Fluid.of('remission:miasma', 250)).energy(4000).time(200).id('counterstrain:synthesizing/serum')`; `.fluidResult(Fluid.of(...))` adds a fluid result, and a recipe with only a fluid result passes `[]` as results. `event.remove({type: 'remission:analyzing'})`, `{id: 'remission:synthesizing/serum'}` or `{type: ..., output: ...}`, `event.replaceInput` and `event.replaceOutput` work on them. The worked sample `.agents/skills/kubejs-scripting/examples/remission_machine_recipes.js` adds, removes and replaces recipes of each type and logs the resulting recipe JSON; copy it into a dev run's `kubejs/server_scripts/` (for example `mod/run/server/`) to check the schemas after a KubeJS or Remission update (P7.3's run: 4 added, 3 removed, 3 modified, 0 failed). It is a sample, not pack content. If ProbeJS does not show the methods, the schema is missing or invalid; fix the mod, do not hand-write `event.custom` workarounds in the pack.

Remission API events (P8.3): server scripts listen through the `RemissionEvents` group, which Remission registers when KubeJS is present (contract, handler list and fields: remission-data-formats, "KubeJS event bindings"). Handlers: `hostCorrupted`, `hostCleansed`, `blockFestered`, `blockPurified`, `chunkStageChanged`, `chunkEnteredRemission`, `strainSpreadAttempt`, `nidusDamaged`, `nidusDestroyed`, `surgeStarted`, `surgeEnded`, `revenantRisen`, `revenantSlain`, `viralLoadChanged`, `strainHazard`, `countermeasureGranted`, `teamLookup`. Fields read as properties (`event.pos`, `event.to.x`, `event.level`, `event.server`; nullable where the Java getter returns `Optional`). Cancel `strainSpreadAttempt`, `nidusDamaged` and `strainHazard` with `event.cancel()` (it ends the handler, so do other work first); scale spread with `event.rateMultiplier = event.rateMultiplier * 0.5` (compose, never overwrite) and nidus damage with `event.amount = ...`; answer `teamLookup` with `event.setTeammates(true)`. Target the hazard events at one hazard: `RemissionEvents.strainHazard('remission:contact', event => ...)`. The queries are bound as `CorruptionQueries`, `TeamQueries`, `StrainHazards` and `BestiaryQueries` (static methods as in Java). Use these for pack-side integrations (for example a Serene Seasons spread multiplier) instead of polling, patching or `NativeEvents`. Worked sample: `server_scripts/remission/nidus_firebreak.js` (a nidus fought down by players leaves a firebreak; `KubeJSBindingTests` runs it). Run-checked gotchas: KubeJS renames some vanilla getters, so `level.getGameTime()` does not exist in scripts; use `level.time` (and `level.dimension` is the dimension ID, not the vanilla method). ProbeJS shows the real names.

Integrations: pack-side tie-ins from DESIGN's Pack integrations table live in `server_scripts/integrations/<modid>.js` (one file per mod, header naming the gate it creates), loaded only when the mod is present (`Platform.isLoaded('<modid>')`).

Names: item, block and fluid IDs, tooltips and lang use the DESIGN glossary (`remission:miasma`, `remission:nidus_core`, "festering"). Anything a script adds that players see (startup-registered items, tooltips, lang, textures under `kubejs/assets/`) is player-facing content: add ledger rows to docs/CONTENT-PROVENANCE.md and mark placeholder textures (content-provenance skill).

Gating: lock items behind Remission data items and samples by replacing inputs or removing and re-adding recipes; record each gate's quest in the script header. Scans (`remission:host_scan`, `remission:block_scan`) match as plain items, or per subject with a `neoforge:components` ingredient on `remission:scan_data` (remission-data-formats, "Scanner and data items"). Balance numbers live in the pack, never in the mod. Test with a playtest instance: `/reload`, then check JEI and `logs/kubejs/server.log` for errors.
